## Conditional source-supported chain

1. Writable projection open configures the live connection for WAL. Repo src/lib.rs:11162 opens it read-write; init_projection_schema begins at :11171 and sets PRAGMA journal_mode = WAL in its schema batch.
2. On writable open, projection_sync_on_open (:14088) compares the stored journal fingerprint with the current journal hash. A normal marker miss reaches the candidate synchronization path after the early return at :14107; projection_sync_existing_candidate (:14122) or projection_rebuild_fresh_candidate (:14140) eventually calls projection_publish_candidate (:13940).
3. projection_publish_candidate runs rusqlite Backup from the candidate into self.projection_db, the already-open live destination connection. SQLite's sqlite3_backup_step resets the destination connection's schemas on completion (sqlite3.c:82439) and commits the destination through sqlite3BtreeCommitPhaseTwo (:82548, implementation :74899). This low-level backup path does not execute doWalCallbacks. If the destination is in WAL mode, sqlite3WalFrames records the commit frame in pWal->iCallback (:69124); sqlite3WalCallback is the function that later returns and clears that pending value (:69297).
4. The first subsequent SQL prepare on that same connection must reload the reset schema. sqlite3LockAndPrepare calls the prepare machinery; sqlite3InitOne (:141992) reads schema entries by executing a nested SELECT * FROM main.sqlite_schema ORDER BY rowid through sqlite3_exec (:142165-142174), then calls sqlite3AnalysisLoad. sqlite3_exec steps the nested VDBE to completion. In SQLite 3.46.0, sqlite3Step starts at sqlite3.c:91128; after VDBE execution returns SQLITE_DONE, sqlite3Step calls doWalCallbacks for autocommit at :91237. doWalCallbacks (:91098) reads/clears the pending WAL callback and invokes the registered hook.
5. SQLite's bundled default threshold is 1,000 WAL frames (:13871-13872), and open registers that default with sqlite3_wal_autocheckpoint (:183343). The default hook (:182201-182209) calls sqlite3_wal_checkpoint when nFrame >= threshold. SQLite documents/implements that function as PASSIVE mode (:182339-182342), equivalent to sqlite3_wal_checkpoint_v2(..., SQLITE_CHECKPOINT_PASSIVE, ...).
6. Therefore, conditionally, a large candidate publication into the live WAL can defer a PASSIVE checkpoint until the first post-publication prepare. The nested schema SELECT then executes during sqlite3_prepare_v3, so checkpoint time is charged to prepare_us; the actual point lookup can still take 37 microseconds. A 1 GB destination makes a large backfill plausible.

This chain is **not runtime-confirmed**. For the saved run, verify that (a) the normal marker missed, (b) projection_publish_candidate completed on the same live connection, (c) the destination WAL had at least 1,000 frames after backup completion, and (d) no intervening SQL statement consumed the callback before the measured props prepare.

Other prepare-time work remains possible if those conditions are false or if the delay persists with auto-checkpoint disabled: schema object parsing and sqliteAnalysisLoad of sqlite_stat tables are explicit in sqlite3InitOne; cold filesystem/VFS I/O is also not excluded by the current timing split.

## Snapshot-manifest caveat for forcing a marker miss

A direct SQL update to the marker in projection.sqlite is **not** a valid way to create the normal incremental marker-miss case when state.json has a P6 manifest:

- The P6 manifest records each snapshot component's byte length and SHA-256, including projection.sqlite. Snapshot creation copies the projection at src/lib.rs:26543 and hashes every component at :26691 before assembling the P6 manifest at :26706.
- Open validation compares the current projection bytes/hash with that manifest at src/lib.rs:26119-26123. A manual marker-row edit changes projection.sqlite bytes, so validation returns projection_valid = false.
- try_load_state then returns LoadedProjectionNeedsRebuild rather than Loaded (src/lib.rs:28150 and :28545-28548). Open sets projection_snapshot_untrusted true for any outcome other than Loaded (:16175-16177), then calls projection_sync_on_open(force_rebuild=true) (:16186). That enters the force-rebuild branch (:14098-14101), creating a fresh replay candidate instead of the normal incremental marker-miss path. It can still publish by backup, but it tests snapshot-digest recovery plus publication, not the ordinary marker-miss candidate-copy/replay path.

If a separate forced-digest-recovery control is desired on a disposable copy, the marker key is src/lib.rs:186, journal_projection_fingerprint_v1, and projection_state is declared at :11197. This SQL is only for that separately labeled path:

    INSERT INTO projection_state(key, value)
    VALUES ('journal_projection_fingerprint_v1', 'forced-stale-bench-copy')
    ON CONFLICT(key) DO UPDATE SET value = excluded.value;

Do not call that an ordinary marker miss and do not repair/re-hash the manifest by hand.

Causal pair on two identical valid-snapshot marker-miss copies: default auto-checkpoint; versus a test-only direct FFI call to sqlite3_wal_autocheckpoint(db, 0) immediately after backup publication and before any SQL on that connection. ## Checkpoint handling implications for a later bounded fix

- Run any explicit checkpoint only after Backup::step returns Done and the rusqlite Backup object has been dropped; then the destination write transaction is over and the mutable borrow is released. The Rust projection mutex is already held for publication.
- PASSIVE is the mode SQLite's default auto-checkpoint uses. It does not wait for readers/writers or invoke the busy handler; it may backfill only safe frames when readers hold snapshots, and it does not truncate the WAL. Partial/busy is a valid outcome; the committed data remains available through WAL and existing read-only snapshots remain valid.
- A direct sqlite3_wal_checkpoint_v2(...PASSIVE...) does not itself clear pWal->iCallback. A later sqlite3Step completion will still consume the pending callback. After a complete explicit pass that later callback is generally a cheap empty pass; if readers pinned frames and the checkpoint was partial, a later callback may make further progress.
- SQL PRAGMA wal_checkpoint(PASSIVE) at the publication boundary causes schema initialization on its own first prepare. That can consume the pending callback there, and the PRAGMA then makes its explicit PASSIVE attempt. This intentionally moves checkpoint work into publication; it does not eliminate the page I/O.
- A checkpoint runs after backup commit/publication, so it cannot make an already-published backup roll back. Do not report a checkpoint error as if publication were rolled back; define post-commit maintenance error handling separately. Do not use FULL, RESTART, or TRUNCATE for this nonblocking publication boundary.
