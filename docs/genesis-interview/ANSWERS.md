# ANSWERS — Genesis (Fable-5) · HQL Cross-Dimension Fusion

> Grounded in working-tree code (`hql.pest`, `ast.rs`, `lib.rs` — dispatch :3354, hybrid_search :3516, neighbors :3681, match_pattern :3037), the pinned `hnsw_rs 0.3.4` source, the GoVibe docs, audits P14–P33, and the HQL/substrate specs. Method: 4 grounding readers → 3 independent designs → 3 adversarial judges; worklog in `docs/genesis-interview/evidence/`.

## A1
**Verdict:** Moat — but narrower than the brief hopes: structural on round-trips and cross-dimension AS-OF consistency; only ~1.5–2.5× on latency vs a *competent* (parallel-leg) composition; and 0× measured to date.
**Reasoning:** In-engine fusion wins when the query genuinely spans dimensions — vector seeds feeding hop expansion feeding fused ranking — because composition pays per-leg IPC (~0.1–1 ms localhost `⚠ ungrounded: standard figure; C1 measures it`) plus serialization of *candidate* sets (K·oversample rows, not final k) plus an app-side id join. Measured legs: vector p50 974 µs @100k/dim-1024/ef200 (AUDIT--P20); hop1 22.6 µs, hop3 2.5 ms (AUDIT--P31); a fused vector→2-hop→RRF pass is plausibly 2–4 ms. The composition floor is **max(legs)+join, not the sum** — a competent app issues the legs concurrently: ~4–5 ms warm. That is a 1.5–2.5× hypothesis, not the 3–5× you get by wrongly summing legs (and P20's Qdrant 3.3 ms p50 went through Docker-on-Windows networking — inflated). Locality is *irrelevant* when: the query is single-dimension (pure vector: Qdrant's AVX2/512 kernels beat scalar hnsw_rs ~4–8×/eval `⚠ ungrounded: architecture estimate` — Cargo.toml:66 enables no SIMD feature, though the crate ships one); candidate sets are huge (serialization amortizes); flows are write-heavy (durable ingest still loses ~13× vs Kuzu COPY — 7.8 s vs 0.6 s, P31); or the composition is itself embedded (LanceDB+Kuzu in-process: RPC tax = 0; the remaining edge is one memory space and no id-join serialization — though LanceDB's vector leg measured 9× slower, P27). Locality is decisive at read:write ≳ 9:1, k ≤ 100, candidate sets 10²–10⁴, selectivity ≥ ~1% `⚠ ungrounded: engineering estimates for C1 to check`. One axis composition cannot match at any latency: a single `AS OF` timestamp applied to both the vector post-filter (lib.rs:3633) and every edge/node check in BFS (:3754/:3789) — Qdrant+Neo4j share no time axis.
**Would change my mind if:** the C1 rig shows a colocated concurrent-leg composition within 1.5× on both p50 and p99 (100k/800k, K=40, depth 2) — then the latency moat is a mirage and the honest claim shrinks to round-trips + consistency + ops.

## A2
**Verdict:** Yes — one *linear, fixed-order, single-instance-per-stage* pipeline survives direct dispatch; it breaks at any query requiring a choice the grammar didn't already make.
**Reasoning:** `HYBRID → TRAVERSE → AS OF → RANK BY` compiles to a fixed 4-slot struct executed by straight-line code, same shape as today's 5-arm match (lib.rs:3399–3499). Each stage maps 1:1 to an existing mechanism: hybrid_search (:3516), a shared-frontier BFS over out_idx/in_idx (:3681), inline temporal checks (:3502), an RRF heap over ≤ K·WIDTH^depth candidates. Direct dispatch fails, specifically, at: (1) **two seed legs joined** — `MATCH … MATCH …`, or a vector leg × lexical leg where either could drive: needs cardinality estimation; (2) **binding selection** — piping a multi-variable pattern row-set into TRAVERSE means choosing which variable is the frontier: a join decision; (3) **cost-based reordering** — filter-before-expand vs expand-before-filter chosen per query; we fix the order (pre-filter binds to the seed; post-expand filtering stays in `apply_hql_clauses`, :2927) and accept suboptimality on adversarial queries; (4) OPTIONAL/branching patterns (outer joins); (5) >3 fusion legs with heterogeneous fetch costs (budget allocation = optimization). The fence must be the **parser**: past-the-line shapes are parse errors with remedy text ("not expressible; compose at the application layer"), never badly-planned executions. One self-warning: selectivity-driven knobs (ef inflation, brute-force-vs-filtered-HNSW threshold) are each O(1) but jointly an embryo cost model — freeze them as published, bench-calibrated constants or they grow adaptive.
**Would change my mind if:** a real GKS/GoVibe consumer produces a load-bearing query needing two traverse stages or a search-reseeding-search join — then the fixed-shape bet is wrong, and the planner-lite-vs-app-side decision must be made explicitly, not by drift.

## A3
**Verdict:** Safe under one written rule; without it, `RANK BY` re-runs K-Impact in slow motion.
**Reasoning:** K-Impact's sin was an engine-owned *composite* (`in_degree·0.5 + tier·0.3 + stability·0.2`) with baked weights that silently degenerated off-domain. The minimal rule that keeps fusion compute-near-data: **the engine ranks only by caller-named, engine-observable rank lists with caller-supplied weights; absent RANK BY it returns results unreordered, and no signal has a default weight.** Corollaries: signals must be raw observables — vector = seed-leg rank, hops = BFS min-depth, recency = recorded_at/valid_from order, `prop.<key>` = a number the *caller* stored — never engine-computed composites. Two consequences the brief hasn't yet accepted: (1) **cut `epistemic` from the engine's signal vocabulary** — after the K-Impact cut there is no grounded engine-side source for it (the only authority signal in the ranking path is `node.impact`, lib.rs:3643, and it's being cut); GoVibe expresses it as `rrf(prop.confidence: 0.8)`, which is *more* caller-parameterized, not less; (2) ship "no RANK BY ⇒ no reorder" as a conformance test, because the first PR that adds a "sensible default weight" reintroduces policy. The precedent is already in the code: hybrid_search's alpha default was silently 0.5 and had to be fixed to 0.0 (comment at lib.rs:3621–3624).
**Would change my mind if:** callers in practice all copy one weight set from the docs — then the policy lives in documentation anyway, and honesty is a *named, versioned preset* the caller opts into: a different, acceptable contract.

## A4
**Verdict:** Not now. Re-keyed HGMem is online community detection wearing a new name; build only after cluster-*retrieval* beats flat HNSW retrieval on a measured task.
**Reasoning:** With qualia removed, "incremental hyperedge clustering on vector similarity" occupies the space Leiden/streaming community detection and GraphRAG communities already own — no differentiation by mechanism, only (possibly) by integration. The engine already ships primitives: `detect_communities` (lib.rs:3841 — majority neighbor-cluster-id propagation into `meta.cluster_id`) and `retrieve_context`'s budget-overflow fallback to `meta_nodes` SuperNodes (:4339–4351). So the real question is not "can we cluster" but "does retrieving via clusters beat flat HNSW + hop expansion on recall/nDCG for GKS corpora." The smallest proving version is **offline**: batch-cluster the default collection, materialize cluster-summary nodes, expose them as a CONTEXT tier, A/B retrieval on the real bge-m3 corpus (P33 protocol). Zero new engine machinery. The stubbed `merge` is the crux precisely because incremental clustering without merge only splits/appends — clusters fragment as data grows and cluster-retrieval recall decays monotonically; merge (stability, hysteresis, re-summarization cost) is where the hard part lives. If the offline A/B shows no retrieval win, incrementality is moot.
**Would change my mind if:** the offline A/B shows ≥5-point nDCG@10 lift (or equal quality at materially lower token budget) — then incrementalize, and the merge design becomes the differentiator worth building.

## B1
**Verdict:** Seven questions, ranked by what kills the program first.
**Reasoning:**
1. **Where is the query log?** The benchmark set is inferred from SDD docs, not observed traffic. If real GKS/MSP traffic is 90% `gks_lookup`, we optimize a moat nobody crosses. Break: months building fusion for queries that never arrive. *Capture 2 weeks of MSP traces before freezing C1.*
2. **Which Qdrant are we racing?** Server-as-deployed (the P20 3.4× "win" is mostly gRPC/Docker tax) or embedded-equivalent kernels (likely a loss — no SIMD)? Break: pick the framing after the numbers and the bench is rigged post-hoc.
3. **What happens to WHERE after S1?** Committed substrate S1 moves node props off the resident map; any native predicate closure over `NodeOutput.props` expires. Break: the G1 filter engine is built twice. *Decide filter ownership (native roaring vs S2 SQL) now.*
4. **Can a 10% bar be falsified inside a ±5–11% run-variance envelope?** (P31 §4: Kuzu hop6 doubled between identical runs; REPORT--HQL-V1-VS-V2 §4.3 sets a ±10% regression envelope.) Break: G1/G2 become unfalsifiable marketing. *≥3 runs, p50+p99, pre-registered criteria.*
5. **Node version history: which committed invariant loses?** The ERD implies supersede-chain walks; WAL compaction (PR #28) destroys history; the substrate spec demands rebuildable projections (§2.2/§4.3). Break: "bitemporal" marketing writes a check the engine can't cash. *ADR before any VERSIONS OF surface.*
6. **Where does text search sit in the fusion?** GoVibe's 4-layer cascade has an FTS leg; the engine has none (trigram index is fuzzy-id-only, lib.rs:2336). Break: `RANK BY` fuses two legs, not four — is that still the product if S3 slips?
7. **What is the pipeline's consistency contract?** Stages read live DashMaps; a node retracted between seed and rank yields anomalies. "Read-committed-per-stage" may be fine — write it down before a consumer files it as a bug.
**Would change my mind if:** n/a — each question names its own falsifier.

## C1
**Verdict:** One rig, three baselines, six query shapes, pre-registered kill numbers.
**Reasoning:** **Dataset:** 100k nodes / 800k edges (fanout 8, P31-comparable) + real bge-m3 1024-dim embeddings (P33 protocol; synthetic 1M as a scale point). Bitemporal texture: 20% of edges retracted/superseded across a simulated 90-day history; labeled props giving filter selectivity {0.1, 1, 10, 50}%. **Queries:** Q1 vector+filter top-10 across the selectivity grid (G1); Q2 `(a{id})-[:LINK*1..d]->(b)` d∈{1,3,6} LIMIT 1000 — the P26/P30 shape (G2); Q3 backlinks (`DEPTH 1 REL ANY DIRECTION in`); Q4 vector K=40 → 2-hop WIDTH 8 → `rrf(vector,hops)` (G3 core); Q5 = Q4 + `AS OF` mid-history; Q6 `CONTEXT … H2 BUDGET 4000` (JIT shape). **Baselines:** (a) server composition Qdrant+Neo4j+TS-RRF with legs issued **concurrently** — deny ourselves the sum-of-legs strawman; (b) **embedded composition** LanceDB+Kuzu+in-process RRF — the strongest fair opponent; (c) us via NAPI *and* REST (one row stays server-vs-server symmetric). Same box, warm and cold both reported (the off-RAM sidecar makes cold a distinct regime — SIDECAR_CACHE_ROWS=4096, lib.rs:1038), ≥3 runs. **Metrics:** recall@10 vs exact-L2 ground truth (Q1); result-set equality vs a reference implementation (Q2–Q5); p50+p99; round-trip count; bytes serialized; peak RSS; for Q5 a **consistency probe**: inject a supersession between the composition's legs and count phantom rows — ours must be 0 by construction. **Falsifiers (pre-registered):** **F1** — embedded composition within 1.5× on p50 *and* p99 for Q4/Q5 ⇒ the latency moat is a mirage: keep `RANK BY` as ergonomics, stop selling fusion as performance, reposition on round-trips + consistency + zero-ops. **F2** — *server* composition with concurrent legs within 1.2× ⇒ even the deployment framing fails; abandon in-engine fusion, ranking returns to the app layer. **F3** — Q1 filtered recall@10 < 0.95 at 1–10% selectivity at ≤2× unfiltered latency ⇒ in-memory filter pushdown insufficient; filtering moves to the S2 substrate. **F4** — Q2 >10% slower than Kuzu prepared Cypher after lazy bindings ⇒ G2 public claim blocked pending profile.
**Would change my mind if:** an external party reproduces the rig and gets a different verdict — every number in this repo is Level 0/1 maintainer-run (docs/benchmarks/INDEPENDENT-BENCHMARKS.md); zero Level-2 reproductions exist.

## Genesis — top recommendation
Focus HQL — but measurement before mechanism. No G3-shape benchmark has ever been run in this repo; the latency margin over a competent composition is plausibly only 1.5–2.5×; yet the structural wins (1 round-trip vs ≥3, and one AS OF timestamp across vector+graph that Qdrant+Neo4j cannot express at any price) are real and already half-implemented. So: capture the pre-P0 baseline first (P0 sits uncommitted in the working tree — a live process risk), land the minimal pipeline surface (`seed THEN TRAVERSE … AS OF … RANK BY rrf(...)` as one fixed 4-slot shape, plus boolean WHERE, var-length paths, WIDTH, DURING), and build **moat-bench as a co-equal deliverable with pre-registered falsifiers** — first G3 number inside ~4 weeks. Wire G1's filter pushdown through hnsw_rs's already-shipped `search_filter` (verified at hnsw.rs:1475 in the pinned crate) only after that number exists. If F1 fires, the honest product is "the embedded cross-dimension database with bitemporal consistency," not "the faster one" — and it is far cheaper to learn that in week 4 than in month 4.
