# ROUND 4 — Genesis (Fable-5) · Engine-Wedge vs Platform-First, Feasibility Lens

> Grounded in a fresh on-disk due-diligence audit (2026-07-07) of all four stack layers plus the engine's product surfaces — evidence with file:line cites in `evidence/r5-rwang.md`, `r5-platform.md`, `r5-engine.md`. The audit answers the fork more decisively than any argument could.

## G-R4.1
**Verdict:** The brief's premise — "we already own a full vertically-integrated stack" — is **falsified on disk**: two of four platform layers do not exist as code. The real per-layer gaps: engine **M**, Rwang **M–L**, GoVibe **L/XL**, GKS **XL**, MSP **XL (greenfield)**.
**Reasoning:** *Engine* — closest to product, yet **a stranger cannot install it today**: the npm package (`@freshair129/gks-genesis-block-native` 0.2.0) is unpublished (registry E404, both names), no v0.2.0 tag exists and the 4-target release workflow has never produced a published artifact (NPM_TOKEN setup unverified), `npm publish --tag beta` is hardcoded, QUICKSTART gives install instructions that contradict package.json (no prepare script exists), SECURITY.md still lists 0.1.0-beta, and the REST server ships as no binary or Docker image. All of this is *packaging*, not engineering — gap M (days-to-weeks). *Rwang* — the audit grade is precise: "dashboard + dry-run planning are clone-and-run today; executing real agents on a stranger's project is author-machine-only." Dispatched agents run in the repo's *parent* directory (`ROOT = resolve(__dir,"..")`, engine.mjs:14 — a stranger's agents get shell access to whatever the clone's parent is), every worker prompt opens with "คุณคือ worker agent ของโปรเจกต์ G-Maiden" (engine.mjs:408) and the ollama agent-hint block hardcodes `root = G:/G-Maiden` (:429-433), `docsForContext` and `scope.byPhase` cite docs that don't exist in the repo (config.json:408-437, :438-519), the knowledge store defaults to the author's engine checkout path (config.json:524), role chains name a personal HF GGUF model, prompts are Thai-only, launcher is Windows-only, no `bin`, npm E404. Nine enumerated gaps, mostly S/M (one M–L) — total M–L. *GoVibe* — two divergent codebases: `G:\govibe` (real dashboard + MCP scripts; no root README, `G:\govibe` literals in every agent script, author session transcripts committed); `D:\GoVibe` (stale scaffold, no git remote, and its `packages/genesis-db` contains exactly one tutorial README.txt — zero engine binding). Gap L for Mission Control, XL for "the platform". *MSP* — **code = NOT FOUND. `G:\msp` exists and is empty.** MSP is an SDD/ADR documentation universe whose own CR marks runtime "out of scope". Gap XL, greenfield. *GKS* — no unified codebase: a 143-line MCP shim in the engine repo (3 tools, stdio, requires a locally-built addon), a **0-byte** `genesis-graph.wal` in `.brain/gks/storage`, and Rwang's `gks/` module — which is a task-atom backlog/marketplace subsystem that shares only the name. Gap XL as a coherent system. Corroborating pattern: even the author's own shipped consumer (NotiKeeper, real APKs) consumes the engine via a hardcoded `require("G:/GenesisBlock_Dev/GenesisBlock/index.js")` (graph-index.mjs:32) — nowhere in the entire estate is the engine consumed through a path-independent, SDK-mediated contract.
**Would change my mind if:** the audit missed a private MSP/GKS runtime repo elsewhere (D: partitions were only spot-checked) — but the burden of proof is now on the platform claim, not against it.

## G-R4.2
**Verdict:** They share the code that matters — **the wedge is on the platform's critical path**, so sequencing is nearly free. Platform-first would not waste the engine/HQL work; skipping the wedge would waste an adapter that *already exists inside Rwang*.
**Reasoning:** By line count: the shared layer is the entire ~6k-line Rust core (storage/WAL, HNSW, graph indices, bitemporal, governance, the whole HQL pipeline) — both a Graphiti/LangGraph driver and GKS/MSP terminate in the same `Storage` methods. Wedge-only code existing today is <1k lines of thin glue (REST server ~680 lines, a 134-line prototype Python SDK, similar Go); platform-only is the NAPI wrapper + the 143-line MCP shim. Three engine work items are demanded by *both* sides: (1) HQL v-next — the platform's own `query_genesis_graph(hops=N)` can't express bounded var-length paths (the P1 item), the same expressiveness a Graphiti driver needs; (2) `events_since` REST exposure — NAPI-only today (no `/v1/sync|events` route), needed by any wedge change-feed and already consumed internally by shadow-sync; (3) bitemporal audit fixes (edge `superseded_by`, supersede-chain enumeration) — demanded by the MSP data model *and* exactly what differentiates a Graphiti backend. The decisive audit finding: **the embryonic wedge driver already exists** — Rwang's `store/genesis-sidecar.mjs` + `store/knowledge.mjs` (~600 lines: in-process binding load, schema pin, embedding shim, addNode/hybridSearch/retrieveContext/GRL wrappers, graceful file-fallback) is precisely the shape a published adapter needs, currently trapped behind a `G:/` default path. Extracting it as a published package simultaneously fixes Rwang's gap #4 and seeds the driver — the single highest-leverage shared artifact in the estate. Two honest wedge-side caveats: the Python channel (Graphiti) rides REST, and the REST server is not shipped as any artifact today; the Python SDK is prototype-grade (88-line client, no auth header support against our own `api_key_guard`, no tests, not on PyPI). Wedge-specific distribution work (driver code, SDK hardening, server packaging) is real but thin — and the packaging item is pure wedge-enablement at zero platform cost.
**Would change my mind if:** Graphiti's driver interface turns out to demand full Cypher semantics our declared HQL subset can't serve (then the driver cost jumps from adapter to translator — verify against their `GraphDriver` contract before committing).

## G-R4.3
**Verdict:** Thinnest-first ordering is unambiguous: **engine (M) < Rwang (M–L) < GoVibe Mission Control (L) < GKS (XL) ≤ MSP (XL, does not exist)**. The minimum viable install-and-go slice is *engine published + the extracted knowledge adapter + an npx-able MCP server* — which is simultaneously the wedge.
**Reasoning:** "Platform-first" is not a shipping decision available today — for MSP and unified-GKS it means *building the product before productizing it*, an XL greenfield on a solo team with zero external users. The genuinely thin slice: (1) **publish the engine** — tag v0.2.0, fire the existing release matrix, fix the dist-tag and QUICKSTART, publish the prebuild optionalDependencies; (2) **extract `genesis-sidecar` + `knowledge.mjs` into a published adapter package** — the first path-independent consumer contract in the estate; (3) make `mcp/server.js` npx-able (bin entry + published package; fix the hardcoded `vectorDim: 1536` that contradicts the bge-m3/1024 default used everywhere else). That slice gives a stranger: `npm install` → embedded bitemporal graph+vector store → MCP memory tools in any client — install-and-go with no orchestrator, no methodology, no 12-stage curriculum. Rwang follows as the *reference consumer* (its 9 gaps are mostly S/M mechanical de-G-Maiden-ing), GoVibe Mission Control after that; GKS/MSP remain internal design programs until a real external pull justifies them. Note what this ordering does to the methodology-adoption-tax concern: the thin slice carries **zero** methodology — the 12-stage/H0–H6 opinions stay in the layers we are *not* shipping yet, which is exactly where they belong until someone asks for them.
**Would change my mind if:** an external party specifically requests the governance methodology (not the engine) — that inverts the demand signal and would justify pulling GKS forward as the product. No such signal exists today (no external adopter found anywhere in the estate, engine included — formal verification of that zero is LYRA's L-R4.1).

## ROUND4 recommendation:
**Hybrid, engine-wedge-first — the specific sequence: (1) publish the engine (verify NPM_TOKEN, tag v0.2.0, fire the release matrix, fix QUICKSTART — days-to-weeks), (2) extract Rwang's genesis-sidecar/knowledge adapter into the first published consumer package (~600 lines already written) and make the MCP server npx-able, (3) ship the REST server as a binary/Docker artifact + SDK auth (the audit's named wedge blocker), then (4) the Graphiti driver on top — gated on first checking their GraphDriver contract fits the HQL subset (the #1240 window) — while Rwang/GoVibe mature privately as reference consumers and MSP/GKS stay internal design programs; platform as destination narrative, engine as the only on-ramp that exists in code;** the single most important thing to verify before committing: **that anyone external pulls the published artifacts at all** — a first-10-installs signal within ~a month of step (1); publishing is nearly free, so measure real demand before spending a quarter on either fork's expensive half.
