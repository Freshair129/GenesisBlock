# ROUND 2 — Genesis (Fable-5) · Positioning Feasibility

> Grounded in working-tree code (cites below), repo audits P20/P26–P31/P33, and fresh 2026-07-06 research on sqlite-vec/libSQL/LanceDB/LadybugDB/DuckDB-vss/Graphiti (citations in `evidence/r2-*.md`). Round-1 baseline: `PROPOSAL.md`.

## G-R2.1
**Verdict:** SQLite assembly is *good enough* below ~50k atoms and *provably wrong* on bitemporal correctness at any scale; the honest moat at this tier is correctness + ceiling + one-query ergonomics — **not** consistency, which SQLite matches in-file. "Only one doing all three" survives, but only in the strict form.
**Reasoning:** *Where SQLite is fine:* sqlite-vec stable (≤0.1.9) is brute-force — the author's own numbers: ~105 ms/query at 100k×1536-dim f32, 11 ms-class with bit quantization (at 3072-dim) — acceptable UX at ≤50k personal scale; recursive CTEs handle depth ≤4 on tens-of-thousands-node graphs "in milliseconds" (practitioner reports; no rigorous CTE-vs-graph-DB benchmark found — itself a citable gap); and critically, one SQLite file gives a serializable snapshot across a vec0 KNN + CTE + temporal WHERE in one transaction (sqlite.org/isolation `⚠ composed inference from documented properties; no published end-to-end writeup`) — **our Round-1 cross-store consistency argument does not apply to this baseline; I concede it here.** *Where it becomes painful/slow:* vector at 100k+ f32 (~50–100× our measured 974 µs p50 @100k dim-1024, P20 `⚠ cross-source comparison, different corpora`), seconds-class at 1M — though **libSQL ships GA DiskANN embedded**, so the SQLite *family* has ANN today and must join the bench, while sqlite-vec's own ANN is a Mar–May-2026 undocumented alpha still fixing ALTER TABLE bugs. Deep traversal: repo evidence has vectorized DuckDB CTE at 52× slower hop1 but only 1.09–1.41× at deep hops (P28/P31); SQLite's row-at-a-time CTE sits below DuckDB `⚠ inference, needs the SQLite row in moat-bench`. *Where it is wrong:* bitemporal. No native temporal tables; every published SQLite pattern is single-axis audit history; bytefish.de documents the structural defect — SQLite "lacks a stable transaction time … throughout multiple triggers" (CURRENT_TIMESTAMP is per-statement) — and we located **no published two-axis, retraction-preserving implementation**. A correctness gap, not a convenience gap. *Axis coverage:* LanceDB = vector + dataset-level version checkout (not row-level bitemporal), no graph. LadybugDB v0.18 = graph + HNSW extension + FTS, no temporal — **one temporal extension away from parity; the nearest engine threat**. Graphiti + FalkorDB Lite approximates all three but as a Python framework over a subprocess, bitemporality app-layer. So the claim must be stated strictly: *the only embedded, in-process engine with engine-enforced row-level bitemporality alongside vector ANN and graph traversal* — naming LadybugDB and Graphiti when we say it. *Restated targets for the embedded tier:* **G1-e**: ≥10× vs sqlite-vec-stable f32 at 100k (ANN-vs-scan, near-certain but unbenched); parity-or-better vs libSQL DiskANN (new, unmeasured baseline); hold the LanceDB margin (P27: ~9× p50 @100k, caveat: recall 0.948 vs 0.998). **G2-e**: already exceeded vs LadybugDB (177× hop1, 7.9× hop3, ~23× hop6, P30/P31); add the SQLite-CTE row. **G3-e**: vs *one SQLite file*, round-trips and consistency tie — the bar becomes (a) a bitemporal correctness suite the DIY stack must pass (retraction, two-axis AS OF, interval overlap) and (b) ≥5× on the fused query at 100k `⚠ hypothesis`, plus lines-of-code-to-working-memory as the honest ergonomics metric.
**Would change my mind if:** a moat-bench run shows the SQLite assembly passing the bitemporal correctness suite and landing within ~2× on the fused query at ≤50k scale — then the personal tier belongs to SQLite and our tier starts where scale or auditability bites.

## G-R2.2
**Verdict:** Near-free is true for a **single-node, single-tenant** sovereign server; false for anything the word "production" usually implies beyond that.
**Reasoning:** Already shipped (code-verified): env-var config with secure-by-default localhost bind (`GENESIS_HOST/PORT/DATA_DIR`, main.rs:19-28), bearer-token auth via `GENESIS_API_KEY` with 401 tests (router.rs:684-702), CORS allowlist (router.rs:709-728), 64 MB/256 KiB body limits (router.rs:678, :627-630), Prometheus `/metrics` outside the auth guard (router.rs:663-673), `/v1/status` + `/v1/version` with schema version. Genuinely missing, with effort class: **container image — none exists in the repo (S)**; graceful shutdown + `save_state()` on SIGTERM (S — main.rs:53 has no shutdown hook); unauthenticated `/health` (S — `/v1/status` is behind the key guard, so orchestrator probes need the secret today); backup/checkpoint REST route (S/M — `save_state()` exists at lib.rs:4537 but is unexposed); TLS (S as documented reverse-proxy, M native); rate limiting (S/M). The real costs: **multi-key auth/roles/per-collection ACL (M/L)** — one static key is all-or-nothing admin; **multi-tenancy (L)** — one global `Storage`, one WAL, one swarm identity; **replication/HA (L)** — the CRDT/Merkle core is real and tested (`reconcile_state` lib.rs:4115, `events_since` :5393) but **no sync wire surface exists**: no `/v1/sync/*` routes, so two REST servers cannot synchronize over HTTP today. P2 answer: yes, it widens the beachhead — ship the Dockerfile + three S-items and market it CouchDB/PocketBase-style as *single-node by design*; do not let the category promise HA.
**Would change my mind if:** the first self-host adopters ask for multi-tenant or HA before they ask for backup and packaging — then "near-free" was the wrong frame and P2 is a second product, not a second deployment mode.

## G-R2.3
**Verdict:** Coherent — substrate vs. surface — provided we never say "SQLite can't" while standing on it.
**Reasoning:** We buy from SQLite exactly what it is best at: crash-safe, boring, universally-trusted durable page storage for props/labels/history projections, *under our WAL's authority* (SPEC--SQLITE-SUBSTRATE §3.1 — SQLite is derived, rebuildable, never authoritative). We add the layer the DIY stack hand-rolls: in-memory HNSW (vs a brute-force scan or an alpha ANN), µs adjacency BFS (vs row-at-a-time CTE), engine-enforced two-axis bitemporality (vs a trigger pattern with a documented stable-timestamp defect), and one query language with fused ranking (vs ~hundreds of lines of SQL + triggers `⚠ ungrounded LOC estimate — measure in the bench as an ergonomics metric`). Precedents that carry this exact story: PocketBase (on SQLite, against Firebase), Turso/libSQL (is SQLite, sells the layer above), Litestream. The tension dissolves because the comparison becomes *same substrate, different query layer* — arguably the cleanest possible framing. One-liner for a developer: **"SQLite stores our bytes; we add what you'd otherwise spend months hand-rolling on it — HNSW vector search, microsecond graph hops, and bitemporal AS OF that trigger patterns are documented to get wrong."** The discipline: our marketing must attack the *assembly*, never the *engine*, and must disclose that the hot path (vectors, adjacency) is native RAM, not SQLite — that's the part they're paying for.
**Would change my mind if:** S1/S2 gates show the substrate leaking into hot-path latency (the SPEC's own traversal-regression gate) — a slow "built on SQLite" is the worst of both framings.

## G-R2.4
**Verdict:** A document *surface* is nearly free and already half-committed; any new *engine* (time-series, OLAP, blobs) is the ArangoDB trap. The rule: surfaces over the existing model — yes; new write paths or storage layouts — no.
**Reasoning:** The engine is *already* a document store: nodes carry arbitrary JSON props; HQL reaches them (`WHERE prop.*`, post-filter today), and the committed S2 substrate compiles exactly these predicates to indexed SQL — so "expose a NoSQL/document query surface" ≈ work already on the roadmap plus JSON-path sugar (`prop.a.b`), cost S. KV is a degenerate case we already serve O(1) via interned ids — free, and not worth marketing as a "model". FTS/BM25 is S3, already planned, one lexical engine. Natural fits stop there. Traps, each refused for an engineering reason not taste: **time-series** — ingest-heavy append + windowed aggregates lands on our worst measured axis (durable ingest ~13× behind Kuzu COPY, P31) and wants a different storage layout; **OLAP/columnar analytics** — we are a row/KV in-memory engine, DuckDB exists; **blob store** — nothing in the WAL/snapshot design wants megabyte values. The line that keeps consolidation coherent (and answers KAIROS): *one data model* — a bitemporal property graph with per-collection vectors — exposed through *several query surfaces* (HQL, document filters, FTS, Cypher-subset patterns). ArangoDB died maintaining N engines and fighting every category at once; surfaces over one model share one WAL, one consistency story, one bitemporal semantics, one test suite. Marketing sentence: "not multi-model — one model, queryable your way."
**Would change my mind if:** real consumers (NotiKeeper/GKS) demonstrate a load-bearing workload — e.g. high-rate telemetry — that the props-over-graph model serves badly; then the choice is *integrate* (ride DuckDB/SQLite for that workload) not *absorb*, and if we ever absorb, the thesis of this answer is dead.

## ROUND2 verdict:
P1 strengthens the case *if* restated honestly (the enemy is the SQLite assembly's correctness ceiling, not its consistency; libSQL's GA DiskANN joins the bench); P2 is a cheap real widening (single-node only — Dockerfile + three S-items; HA/tenancy are different products); P3 is coherent (substrate-vs-surface, PocketBase precedent) so long as we attack the assembly, never the engine; P4: document-*surface*-over-existing-model is nearly free, new engines are the ArangoDB trap; the most important next act — **run moat-bench with the SQLite+sqlite-vec+CTE (+libSQL-DiskANN) assembly as primary baseline, including the bitemporal correctness suite, before any positioning ships.**
