## name

Path A — "HQL/1 Fused Pipeline": fixed-shape in-memory pipeline DSL with roaring pre-filter pushdown, W/H-bounded BFS, inline bitemporal intervals, and streaming RRF

## thesis

Keep the entire engine inside the current DashMap+HNSW+roaring substrate and redefine HQL as a *fixed-shape pipeline*, not a query language with a planner: exactly one source stage (SEARCH/HYBRID vector leg, or TRAVERSE/MATCH graph leg), at most one EXPAND (graph-hop) stage, at most one temporal projection (AS OF two-axis point, or DURING interval), and at most one terminal RANK BY rrf(...) fusion — each stage compiled 1:1 to a hand-fused native operator dispatched from `execute_hql` (src/lib.rs:3354) exactly like today. The three new engine mechanisms are (1) a filter pushdown: new roaring bitmap secondary indexes (`label_idx`, opt-in payload-value bitmaps, reusing the `roaring = "0.10"` dep already at Cargo.toml:87 and the pattern of `trigram_index: DashMap<String, RoaringBitmap>` at lib.rs:1575) intersected into ANN via `hnsw_rs 0.3.4`'s **already-shipped** `Hnsw::search_filter(..., Option<&dyn FilterT>)` (verified in the pinned crate: filter.rs:7-19 blanket-impls FilterT for closures; hnsw.rs:1475; the seam is `VecIndex::search_f32`, lib.rs:994-1031, which today calls plain `h.search`), with a single cardinality-threshold switch to exact brute-force over the bitmap at low selectivity (extending the existing brute-force escape hatch at lib.rs:3576-3596); (2) traversal upgrades inside the existing BFS (`neighbors`, lib.rs:3681-3820): per-node FANOUT cap (W-scale), H-tier depth sugar, wildcard REL, interval checks inlined next to the existing `is_valid_as_of` calls (lib.rs:3753-3767); (3) a caller-parameterized streaming RRF fuser over the bounded candidate set the pipeline produces. This attacks G3 with structural locality (one process, zero round-trips, one memory space — vs Qdrant+Neo4j+app-RRF paying >=3 RPCs and full serialization per leg) and G1 with the filter-aware ANN the engine currently lacks entirely (grounding: "No attribute/property filter exists anywhere in this path", hybrid_search §1).

## grammar_sketch

New/changed pest rules (src/query/hql.pest; all additions keep every v1/v2-P0 query parsing identically):

```
// ---- boolean pre-filter (pushed down; old WHERE stays post-process) ----
filter_or   = { filter_and ~ (^"OR" ~ filter_and)* }
filter_and  = { filter_fac ~ (^"AND" ~ filter_fac)* }        // AND binds tighter (matches SPEC--HQL-V2 §4.1)
filter_fac  = { (^"NOT")? ~ (predicate | in_pred | range_pred | "(" ~ filter_or ~ ")") }
in_pred     = { field ~ ^"IN" ~ "[" ~ value ~ ("," ~ value)* ~ "]" }
range_pred  = { field ~ ^"BETWEEN" ~ value ~ ^"AND" ~ value }
pre_filter  = { ^"FILTER" ~ filter_or }
// ---- temporal ----
as_of       = { ^"AS" ~ ^"OF" ~ (^"VALID")? ~ string_lit ~ (^"SYSTEM" ~ string_lit)? }   // supersedes hql.pest:25, back-compat
during      = { ^"DURING" ~ "[" ~ string_lit ~ "," ~ string_lit ~ ")" }                   // valid-time overlap, closed-open
temporal    = { as_of | during }
// ---- traversal bounds ----
h_tier      = { ^"H" ~ ASCII_DIGIT }                          // H0..H6 sugar; H6 = closure w/ mandatory frontier cap
depth_spec  = { ^"DEPTH" ~ (depth | h_tier) }
fanout_spec = { ^"FANOUT" ~ number }                          // W-scale per-node per-hop cap
rel_any     = { "*" }                                         // wildcard REL (gks_backlinks shape)
// ---- var-length in patterns (SPEC--HQL-V2 §3.1, unchanged) ----
rel_detail  = { "[" ~ var? ~ (":" ~ ident ~ ("|" ~ ident)* )? ~ ("*" ~ digits ~ ".." ~ digits)? ~ "]" }
// ---- pipeline (fixed order, fixed arity — THIS is the no-planner guarantee) ----
expand      = { ^"EXPAND" ~ ^"REL" ~ (rel | rel_any) ~ depth_spec ~ direction_spec? ~ fanout_spec? }
rrf_arg     = { ident ~ ":" ~ number }                        // vector|hops|recency|degree|k
rank_by     = { ^"RANK" ~ ^"BY" ~ ^"rrf" ~ "(" ~ rrf_arg ~ ("," ~ rrf_arg)* ~ ")" ~ (^"K" ~ k)? }
pipeline    = { (search | hybrid) ~ pre_filter? ~ expand? ~ temporal? ~ rank_by? ~ clauses }
query       = { SOI ~ (pipeline | traverse | match_pattern | context) ~ EOI }
```

## g1

MECHANISM. (a) New secondary indexes in `Storage`: `label_idx: DashMap<String, RoaringBitmap>` (node u32s per label) plus opt-in payload bitmaps `payload_idx: DashMap<(String, String), RoaringBitmap>` for fields registered via a new `create_payload_index(field)` — maintained at `add_node`/`supersede_node`/batch commit, rebuilt on snapshot load exactly like `trigram_index` is (lib.rs:4888-4890). (b) FILTER compiles (in the AST, no planner) to a roaring expression tree evaluated once per query into a node-u32 bitmap; unindexed predicate leaves fall back to a scan-and-materialize of that leaf's bitmap (correct, slower, WARN-tagged in the response). (c) The bitmap is mapped node_u32→arena_id via `node_to_arena` (lib.rs:1242-1293) and pushed into ANN with a two-regime cardinality switch — an O(1) decision, not a cost model: Regime A (|bitmap| <= T, default T = max(k*RERANK_OVERFETCH*4, 4096), bench-calibrated): skip HNSW, exact-score every bitmap row through the existing sidecar/arena rerank path — a direct generalization of the existing brute-force escape hatch (lib.rs:3576-3596); ~4096 scalar-L2 evals at dim 1024 ≈ low-single-digit ms worst case, and at GKS-realistic selectivity (hundreds of atoms) ≈ tens of µs with PERFECT recall. Regime B (|bitmap| > T): `h.search_filter(query, fetch, ef_eff, Some(&closure))` where the closure tests `bitmap.contains(arena_id)` — VERIFIED available in the pinned hnsw_rs 0.3.4 (hnsw.rs:1475; filter applied at result-collection while navigation traverses the full graph per hnsw.rs:983-1035, i.e. it does not get stuck in filtered-out regions), wired at the single seam `VecIndex::search_f32` (lib.rs:994-1031) with `ef_eff = min(ef/max(s, 0.05), 4*ef)` where s = |bitmap|/N. Selectivity math for the boundary: brute cost ≈ s*N exact evals; filtered-HNSW ≈ ef_eff visits; crossover at s*N ≈ few*k*oversample — hence T. (d) Latency budget: unfiltered p50 is already 974 µs @100k ef200 (AUDIT--P20) vs Qdrant-server 3,301 µs on the same corpus; the +10% target vs Qdrant-over-gRPC has ~3x headroom purely from being embedded. VERDICT: latency bar REACHABLE with high confidence against Qdrant-as-deployed (server); it is honestly a category advantage, not an algorithmic one — state that in the bench doc. Expressiveness bar NOT fully reachable: AND/OR/NOT + exact match + IN + BETWEEN range covers Qdrant's must/should/must_not/match/range core, but geo, nested-object filters, and full-text `MatchText` are out of scope for Path A (no BM25 leg — trigram index is fuzzy-id-only, lib.rs:2336-2381). RENEGOTIATE G1 expressiveness to "the filter algebra GKS/GoVibe actually emits (label/status/type/id-set/time-range)". Recall parity under filters at mid selectivity (1-20%) is a HYPOTHESIS until the filtered-recall bench runs — no filtered-search comparison exists in-repo at all (grounding 4 §5: "G1 has no prior evidence base").

## g2

MECHANISM. The traversal shapes GoVibe actually needs (grounding 3 §4: k-hop bounded expansion with fan-out cap, backlinks, supersede-chain walk, var-length reachability) map onto: (a) SPEC--HQL-V2 §3.1 var-length `-[:R*min..max]->` implemented as bounded frontier expansion inside `match_pattern` (lib.rs:3037-3222) reusing the `neighbors` BFS discipline (visited set — which match_pattern currently LACKS, grounding 1 §3 "no cycle guard"); (b) FANOUT n = per-node candidate cap applied after the rel/direction filter inside the BFS loop (deterministic: take first n by sorted edge u128 key), plus the frontier row cap of SPEC §3.2 (hard error, not truncation); (c) LIMIT pushdown: wire HQL LIMIT into the existing-but-unused `NeighborInput.limit` early-exit (lib.rs:3805-3809, currently hardcoded None at 3453); (d) lazy bindings (PLAN P1-T3): stop serializing full node+edge JSON per row in match_pattern (lib.rs:3157-3163) and stop cloning the full path Vec per expansion in neighbors (lib.rs:3797-3798, O(depth^2)) — project only RETURN-referenced fields. Evidence base: GB is ALREADY 6.8-23x faster than Kuzu and 7.9-177x than LadybugDB on hop1/3/6 at 100k/800k (AUDIT--P26/P30/P31, like-for-like embedded), and near-parity-or-better vs DuckDB at deep hops (1.09x hop6) — the <=10% bar on traversal latency is not just reachable, it is already exceeded on every measured hop shape; P1 makes it expressible in HQL itself for the first apples-to-apples HQL-vs-Cypher head-to-head (REPORT--HQL-V1-VS-V2 §4.4). VERDICT: REACHABLE on the named shapes, with two honest exclusions: (1) "Cypher subset" must be renegotiated to the enumerated list — linear patterns, var-length, rel-alternation, OR/NOT WHERE, count(*); NO OPTIONAL MATCH, branching patterns, path variables, shortest-path, or general aggregation (SPEC--HQL-V2 §7 non-goals stand); (2) G2 explicitly excludes bulk ingest (Kuzu COPY wins ~60x) and RSS (~7x, columnar vs 3.6 KB/node resident floor) — those are the S1 substrate's problem, not HQL's, and claiming otherwise would be dishonest. Deep-hop numbers carry the payload-materialization confound (P29) until lazy bindings land — re-bench after (d).

## g3

MECHANISM. E5's pipeline executes as one fused native pass in a new `Storage::execute_pipeline` (lives in src/lib.rs next to execute_hql per the one-big-file convention): stage 1 vector leg = filtered `hybrid_search` producing K=32 seeds with their similarity ranks (candidate struct: {node_u32, vec_rank, sim}); stage 2 EXPAND = the neighbors BFS seeded with ALL 32 seeds at once (multi-seed BFS, visited-set shared), FANOUT 8, DEPTH 2, recording per-result min-hop depth; the temporal projection is INLINE in that same loop (the existing per-edge/per-node `is_valid_as_of` call sites at lib.rs:3753-3767/3789-3795 extended to the two-axis/interval forms) — no separate pass; stage 3 RANK BY = compute per-signal ranks over the bounded candidate set (<= 32 * 8^2 = 2048 candidates by construction — the caps make rank computation trivially cheap) and fuse with score = Σ w_i/(k_rrf + rank_i) into a BinaryHeap top-K. Signals are engine-observable only (domain-neutral guardrail): vector = rank in the seed leg (non-seed candidates get rank ∞, i.e. contribute 0), hops = min BFS depth, recency = rank by valid_from desc, degree = rank by |out_idx[u]|+|in_idx[u]|. Latency budget from measured numbers: filtered HNSW ~1-1.5 ms @100k ef256 (P20/P21 frontier) + multi-seed depth-2 fanout-capped BFS — hop1 is 22.6 µs and hop3 2.5 ms UNCAPPED at fanout-8/LIMIT-1000 (P31), so a fanout-8-capped 2-hop from 32 seeds is sub-ms-to-low-ms + RRF over <=2048 rows ≈ tens of µs → end-to-end ≈ 2-4 ms, ONE round trip. App composition: Qdrant gRPC leg alone measured 3.3 ms p50 (P20), plus a Neo4j bolt k-hop leg (GB is 8.5-185x faster than Neo4j on hops, P23, so their leg is ms-to-tens-of-ms), plus per-leg serialization, plus app-side RRF, >=3 round trips. VERDICT: decisive win vs the named composition (Qdrant+Neo4j+TS-RRF) is REACHABLE with high confidence — round-trips 1 vs >=3 is structural and unarguable, latency plausibly >=3-5x. HONEST CAVEATS: (1) no G3-shape benchmark has EVER been run (grounding 4: "nothing measures a single query spanning vector+hop+AS-OF+fusion") — this is a hypothesis until the new bench exists; (2) against a best-case EMBEDDED composition (LanceDB + Kuzu-embedded + in-process RRF) the RPC advantage vanishes and the win rests on shared memory space / no cross-store id-join serialization — likely still a win (LanceDB is 9x slower on the vector leg alone, P27) but the bench MUST include this config or the "decisive" claim is rigged; (3) recall interaction: seeds dropped by the AS-OF post-filter shrink the fused set — the pipeline mitigates by applying temporal checks inside BFS rather than after truncation, but the vector leg's as_of remains a post-filter with no top-up refetch (lib.rs:3633-3639) — fix by folding as_of into the FILTER bitmap when DURING/AS-OF is present (valid_from/valid_to are just strings; a scan-built temporal bitmap leaf is correct if slow).

## interval_semantics

SYNTAX. (1) `AS OF "<t>"` — unchanged v1 valid-time point projection (back-compat, parses identically). (2) `AS OF VALID "<tv>" [SYSTEM "<tx>"]` — two-axis bitemporal point per GoVibe ERD §4: entity passes iff valid_from <= tv < valid_to (existing `is_valid_as_of`, lib.rs:3502-3514, lexicographic RFC3339 compare) AND, on edges, recorded_at <= tx (EdgeOutput carries recorded_at, lib.rs:156-169). (3) `DURING ["a","b")` — valid-time interval OVERLAP: passes iff valid_from < b AND (valid_to is null OR valid_to > a); implemented as a sibling of is_valid_as_of, same string-compare technique, inlined at the same three call-site families (hybrid_search post-filter lib.rs:3633, neighbors per-edge/per-node lib.rs:3753/3789, match_pattern lib.rs:3120/3151). (4) Hop-interval + governance scales: `DEPTH H0..H6` sugar maps H-tier→hops per STD §3 (H0=0 … H5=5; H6 = transitive closure, reusing the is_inferred unbounded-depth path lib.rs:3732 but REQUIRING a frontier cap — no cap, parse error); `FANOUT <n>` = W-scale per-node per-hop breadth cap (W2 optimal=3-5, W4 danger=9+ per STD §4 — engine takes the number, never the policy). EXECUTION: all interval checks are per-row inline string compares in the already-hot loops — zero new data structures, zero temporal index (honest cost: O(rows-visited), fine because FANOUT/DEPTH bound rows-visited; a temporal index is explicitly deferred). HONEST LIMITS, stated not hidden: (a) tx-time on NODES is impossible — NodeOutput has no recorded_at (lib.rs:121-138) and `supersede_node` overwrites the in-memory slot (lib.rs:2777-2812), so historical node versions exist only in the WAL; `AS OF VALID` on nodes projects only the CURRENT version's validity window. Full node time-travel requires either WAL replay or the version-chain being resident — out of Path A scope, renegotiated to "edges fully bitemporal, nodes valid-time-current-version". (b) EdgeOutput.superseded_by is never set by any write path (add_edge sets None, lib.rs:2765) — the ERD's supersede-chain walk is expressible as `TRAVERSE ... REL caused_by` over the caused_by lineage instead; wiring superseded_by is a small write-path fix worth doing but is a data-model change, flagged separately. (c) `include_invalid` gets HQL surface as `DURING [.., ..] INCLUDE RETRACTED` (today hardcoded false, lib.rs:3452).

## planner_line

THE LINE: direct dispatch survives exactly as long as every execution decision is either (a) fixed by grammar position or (b) a single O(1) threshold comparison. This design stays inside by construction: the pipeline grammar admits ONE source, at most ONE expand, ONE temporal, ONE rank — order fixed in the pest rule, so "plan" = the parse tree itself; the only runtime choice is the two-regime filter switch, decided by one `bitmap.len() <= T` comparison (an escape-hatch idiom the engine already uses at lib.rs:3576, not a cost model). DISPATCH FAILS PAST: (1) two or more source legs whose join order matters (e.g. `MATCH ... MATCH ...` or fusing a lexical leg with a vector leg where either could drive) — that needs cardinality estimation; (2) stage reordering for cost (filter-then-expand vs expand-then-filter chosen per query when both filters and expansion are selective) — we FIX the order (filter binds to the source leg only; post-expand filtering is the old WHERE post-processor, apply_hql_clauses lib.rs:2927) and accept the suboptimal plan on adversarial queries; (3) arbitrary boolean combination of sub-QUERIES (not predicates) — OR of two pipelines is app-side; (4) OPTIONAL MATCH / branching patterns — outer-join semantics need binding-aware plans; (5) more than ~3 RRF legs with heterogeneous fetch costs, where leg budget allocation becomes an optimization problem. Each of these is a named grammar non-goal (SPEC--HQL-V2 §7 extended), so the tar-pit is fenced at the parser: queries past the line are UNPARSEABLE, not badly-planned.

## risks

(1) Filtered-HNSW recall at mid selectivity (1-20%) — hnsw_rs's search_filter filters at result-collection while navigating the full graph (hnsw.rs:983-1035), which avoids graph-disconnection pathologies but means visited-budget is spent on filtered-out points; ef inflation may not fully compensate. Mitigation: the brute-force regime floor guarantees exact results at low selectivity; bench regime boundary explicitly. (2) RSS creep from bitmap indexes — roaring is compact but label/payload cardinality is unbounded; cap payload indexing to explicitly registered fields; measure on the P31 RSS harness. (3) Write-path cost: every add_node/supersede now touches label_idx (and payload bitmaps) — DashMap+roaring insert is cheap but must be benched against the 1,897-2,236 vec/s ingest baseline (P33). (4) match_pattern var-length + visited-set changes row semantics for cyclic graphs — `*1..1` MUST stay row-identical to single hop (SPEC §3.1 invariant), pin with tests. (5) Fuzz surface triples — P0-T8's unextended mutation generators are existing debt; new keywords (FILTER/EXPAND/DURING/RANK BY/FANOUT) must enter the corpus or the never-panic guarantee silently narrows. (6) NAPI/REST drift — execute_pipeline must be wired in both front-ends (CLAUDE.md warning); HybridSearchInput grows a filter field, REST body compat via serde defaults. (7) Bench fairness attack surface: the G1 headline leans on embedded-vs-server; publish both framings or credibility (currently Level 0/1 only, zero external reproductions) suffers. (8) Concurrent mutation during a multi-stage pipeline: stages read DashMaps without a snapshot — a node retracted between stage 1 and stage 3 can yield anomalies; document read-committed-per-stage semantics (same as today's single commands). (9) Collision with the SQLite substrate program (S2 wants WHERE/OR pushed to SQL): Path A's FILTER bitmaps and S2's SQL filters overlap — governance decision needed on which owns boolean filtering long-term, else two filter engines drift.

## honest_assessment

Where the stated bars are NOT reachable as written, with fallbacks: G1 EXPRESSIVENESS — "match Qdrant query-DSL" is not reachable in Path A: no geo filters, no nested-object payload filters, no full-text MatchText (the trigram index is fuzzy-id resolution only, lib.rs:2336-2381; BM25/lexical is the S3 substrate's job). FALLBACK: renegotiate to "the filter algebra GKS/GoVibe emits" (boolean core + match + IN + range) with a published gap table; G1 LATENCY stands but must be published with the embedded-vs-server framing explicit — it is a deployment-category win, and an embedded-fair comparison (Qdrant local mode, or acknowledge none exists in Rust) must appear in the bench doc. G2 — reachable on the enumerated traversal shapes (already exceeded on all measured hop shapes), but "expressively equivalent to a Cypher subset" only holds for the enumerated subset; OPTIONAL MATCH/branching/aggregation/shortest-path are permanent non-goals, and ingest/RSS losses (48-60x, ~7x vs Kuzu-family) are explicitly OUTSIDE the G2 bar — anyone reading the claim must see that exclusion. G3 — the round-trip win is structural and safe; the "decisive latency" claim is an untested hypothesis (no G3-shape bench has ever existed in this repo), and the honest bench must include the strongest embedded composition (LanceDB+Kuzu-embedded+in-process RRF), where the margin shrinks from "RPC tax" to "shared memory space + no id-join serialization" — if that config only ties, the moat narrative must be downgraded from latency-moat to integration/DX-moat (1 query, 1 store, 1 consistency domain, bitemporal for free). BITEMPORAL — full two-axis time-travel on NODES is not deliverable from RAM (no recorded_at on nodes, supersede overwrites the slot, history is WAL-only): shipped scope is "edges fully bitemporal, nodes valid-time current-version", which covers the GoVibe ERD's edge-shaped state records (assignments/handoffs/verifications) but NOT arbitrary node version archaeology — that requires the substrate or WAL-replay work and should be said out loud in the spec.

## switch_trigger

Abandon (or subordinate) Path A if any of: (1) STAGE-A bench shows filtered recall@10 < 0.95 in the 1-20% selectivity band at <=2x unfiltered latency after ef inflation AND the brute-force threshold cannot be raised without blowing the latency budget — that means in-memory filter pushdown can't reach Qdrant-class filtered recall, and boolean filtering should move to the SQLite substrate (S2's indexed SQL pre-filter producing the candidate id-set) with Path A retained only for fusion/traversal; (2) the G3 bench vs the STRONGEST embedded composition shows <1.5x end-to-end latency win — the latency moat is a mirage; renegotiate G3 to round-trips/consistency/DX and stop the fused-operator investment past Stage C; (3) bitmap index maintenance regresses durable ingest >10% on the P33 harness or RSS >5% on the P31 harness with GKS-realistic label cardinality — the in-memory index tax is too high, filtering belongs in the substrate; (4) the RRF candidate sets GoVibe actually needs exceed the fixed-shape caps (evidence: real GKS queries needing >3 legs or needing lexical as a leg NOW) — the pipeline shape is wrong and the design needs the S3 lexical leg first, i.e. sequencing inverts to substrate-first. Each trigger is a measurable gate attached to a named stage, so the decision point arrives with evidence, not vibes.
