## name

Path B — Substrate-Leveraged HQL: native vector + SQL-compiled predicates + Rust-fused pipeline

## thesis

Keep HQL a linear, fixed-shape pipeline DSL with direct dispatch (execute_hql stays a flat match, src/lib.rs:3354), but split execution by what each substrate is structurally good at: HNSW and adjacency hops stay native in-memory (hop1 22.6 µs, AUDIT--P31 — the crown jewel SQLite must never touch), while everything that today is a scan-with-no-key — label anchors (full DashMap scan, lib.rs:3078-3091), property predicates (post-filter after top-K, lib.rs:2927), temporal range/interval predicates (per-row string compare, lib.rs:3502-3514), count/anti-join aggregates — compiles to SQL over the already-committed engine-owned SQLite projection (docs/SPEC--SQLITE-SUBSTRATE-S0-S1.md; WAL stays sole authority, §3.1). The two worlds meet on u32 node ids only: SQL predicate evaluation returns a RoaringBitmap of node_u32 that (a) feeds hnsw_rs's native `search_filter`/`FilterT` (verified present in the pinned 0.3.4: registry src/filter.rs:7-24, hnsw.rs:1475) for filter-aware ANN, and (b) semi-joins traversal frontiers in one batched query, never per-row. Fusion is a new caller-parameterized RANK BY rrf(...) operator executed in Rust over rank lists of u32 ids — zero serialization between stages, full-row materialization only for the final LIMIT k (killing the P29 payload confound). The SQLite projection additionally gives us the one thing the in-memory model structurally cannot: node version history (supersede_node overwrites the RAM slot, lib.rs:2777-2812 — old versions survive only in WAL), enabling true two-axis bitemporal AS OF as append-only `node_versions` rows. SQLite's own planner does the predicate work; our Rust code makes exactly one decision (a cardinality threshold), which is how we stay out of the planner tar-pit.

## grammar_sketch

Grammar (src/query/hql.pest v-next; every v1/v2 query still parses — new surface is additive):

  pipeline   = SOI ~ seed_stage ~ traverse_stage? ~ temporal_stage? ~ rank_stage? ~ clauses ~ EOI
  seed_stage = search | hybrid | match_pattern | traverse | context      // any existing command
  traverse_stage = "|>" ~ ^"TRAVERSE" ~ (^"REL" ~ rel)? ~ depth_range ~ width_cap? ~ direction_spec?
  depth_range    = ^"DEPTH" ~ n ~ (".." ~ n)?          // DEPTH 2  or  DEPTH 1..6 ; TIER H0..H6 sugar → hops (H6 = unbounded ceiling, STD--Execution-Governance §3)
  width_cap      = ^"WIDTH" ~ n                        // per-hop fan-out cap (W-scale, STD §4)
  temporal_stage = as_of2 | during
  as_of2  = ^"AS OF" ~ (string_lit | ^"VALID" ~ string_lit ~ (^"SYSTEM" ~ string_lit)?)
  during  = ^"DURING" ~ "[" ~ string_lit ~ "," ~ string_lit ~ ")"       // interval overlap
  rank_stage = ^"RANK BY" ~ ^"rrf" ~ "(" ~ (^"k" ~ ":" ~ n ~ ",")? ~ (signal ~ ":" ~ number)+ ~ ")"
  signal  = "vector" | "hops" | "recency" | "text" | "prop." ~ ident    // epistemic = caller's own prop signal — engine imposes no policy
  filter_expr (replaces flat AND-only where): expr = term (OR term)* ; term = factor (AND factor)* ; factor = [NOT] pred | "(" expr ")"   // per SPEC--HQL-V2 §4.1 + NOT
  var-length pattern: -[r:REL*1..3]-> per SPEC--HQL-V2 §3.1

Six concrete examples:
1. G1 vector+filter:  SEARCH doc-7 K 20 EF 200 OVERSAMPLE 8 IN default WHERE (label = "SPEC" OR prop.status = "active") AND NOT prop.tier = "MASTER"
   → WHERE compiles to SQL over node_labels/node_props indexes → bitmap → filtered HNSW (pre-filter, not post-truncation).
2. G2 var-length + bounds:  MATCH (a {id:"g0"})-[:LINK*1..6]->(b) WIDTH 8 RETURN b.id LIMIT 1000   // the P26/P30 bench query, now first-class; WIDTH enforces W3
3. Two-axis bitemporal:  TRAVERSE FROM task-42 DEPTH 2 REL ASSIGNED_TO AS OF VALID "2026-06-01T00:00:00Z" SYSTEM "2026-06-15T00:00:00Z"
4. Interval overlap:  MATCH (n:ROADMAP_NODE) DURING ["2026-05-01T00:00:00Z","2026-06-01T00:00:00Z") RETURN n.id, n.prop.version   // sprint-window query the GoVibe ERD implies
5. G3 moat query:  HYBRID "auth refactor" K 20 EF 200 |> TRAVERSE REL DEPENDS_ON|BLOCKS DEPTH 1..2 WIDTH 8 DIRECTION both |> AS OF VALID "2026-06-20T00:00:00Z" |> RANK BY rrf(k:60, vector:1.0, hops:0.5, recency:1.2, prop.confidence:0.8) LIMIT 10
6. Version history (gks/GoVibe supersede-chain):  VERSIONS OF task-42 DURING ["2026-05-01T...","2026-07-01T...") ORDER BY recorded_at DESC   // reads append-only node_versions rows in SQLite — inexpressible against the in-memory map

## g1

Mechanism: (1) Extend substrate schema (S2') with `node_labels(node_u32, label)` (already in S0 schema v1, SPEC--SQLITE-SUBSTRATE §4.2) plus `node_props(node_u32, key, value_text, value_num)` EAV with composite indexes — B-trees give us what DashMap has no answer for: predicates with no key. (2) WHERE compiles to one SQL SELECT returning node_u32s → RoaringBitmap → map via `node_to_arena` (lib.rs VectorCollection) to arena-id allowlist. (3) Two-way cardinality rule (a constant threshold, not a planner): if |bitmap| ≤ max(4·k·oversample, 10k) → exact brute-force scoring over the allowlist via the off-RAM f32 sidecar (generalizes the existing escape hatch, lib.rs:3576-3596 — this is precisely Qdrant's "payload-index pre-filter + exact" strategy); else → `hnsw.search_filter(query, fetch, ef, Some(&bitmap_closure))` — GROUNDED: hnsw_rs 0.3.4 ships FilterT + search_filter (registry hnsw_rs-0.3.4/src/filter.rs, hnsw.rs:1475), so filtered candidates are rejected DURING graph descent, not post-truncated; recall loss of post-filter disappears. Expressiveness: AND/OR/NOT/parens + range + CONTAINS/STARTSWITH + IN-list covers Qdrant's must/should/must_not + match/range core. Verdict: latency bar REACHABLE-LIKELY but with an asterisk — no embedded-fair Qdrant comparison exists in-repo (AUDIT--P20 was server-mode; the 3.4× p50 "win" was mostly localhost-gRPC tax, explicitly flagged). Against Qdrant-as-deployed (server) we should beat by far more than 10% on p50 for in-process consumers (that IS the honest MSP deployment comparison); against a hypothetical embedded Qdrant the outcome is unmeasured. Expressiveness parity: PARTIAL by design — geo filters, nested-object filters, named/sparse vectors are declared out of scope (renegotiated, engine stays domain-neutral). Mid-selectivity filters (10-50% pass rate) are the known weak zone of every filtered-HNSW; we publish that curve rather than hide it.

## g2

Mechanism — and this is where honest Path B refuses to over-apply its own bias: traversal stays NATIVE. Evidence: our BFS over out_idx/in_idx is 120-189× faster than Neo4j/Kuzu at hop1 and 7-23× at hop3/6 (AUDIT--P23/P26/P31), while DuckDB's recursive CTE — a better CTE engine than SQLite's — only reaches 1.09-1.41× of us at deep hops and loses 52× at hop1 (P28/P31). Compiling hops to SQLite CTEs would burn a 100× advantage to gain nothing. So: (1) var-length `-[:R*1..3]->` and DEPTH ranges execute in the existing neighbors BFS (lib.rs:3681-3820) with min-depth emission and the already-present-but-unused `NeighborInput.limit` pushdown (lib.rs:3805-3809); (2) WIDTH executes as deterministic per-node truncation of the deduped eid set (after lib.rs:3737-3747, sorted by edge key for stability); (3) SQLite contributes exactly three things — indexed label anchors for MATCH (replacing the full node scan at lib.rs:3078-3091), batched frontier semi-joins for property predicates (`WHERE node_u32 IN (frontier)` — one prepared statement per hop, never per row), and `count(*)`/anti-join aggregates (broken-link enumeration, drift counts per SDD-Symbol-Graph §6) which today are inexpressible; (4) lazy bindings (P1-T3) stop serializing full node+edge JSON into every row (lib.rs:3157-3163). Verdict: the ≤10%-slower latency bar is REACHABLE with enormous margin — we are currently orders of magnitude FASTER on exactly the GKS shapes (query_genesis_graph = k-hop bounded expansion, gks_backlinks = 1-hop in-edges). The honest framing of the risk: the bar is not latency, it is expressiveness equivalence — and we meet only a DECLARED Cypher subset (linear patterns, var-length, boolean WHERE, count(*)); OPTIONAL MATCH, branching patterns, shortest-path, general aggregation stay non-goals per SPEC--HQL-V2 §7. Also on record: Neo4j/Kuzu still win bulk ingest ~60× and RSS ~7× (P26/P31) — outside the G2 bar, but S1 props-migration is the RSS answer.

## g3

Mechanism — the pipeline is one in-process function chain over u32 ids: Stage 1 `hybrid_search` (native HNSW, overfetch K·oversample, optionally bitmap-filtered per G1) → Vec<(u32, sim)>. Stage 2 native BFS from each seed with DEPTH/WIDTH/DIRECTION/rel-union bounds, recording hop distance per reached node; per-edge two-axis temporal check uses the existing bitemporal edge fields valid_from/valid_to/recorded_at/superseded_by (lib.rs:156-169) — a string-compare extension of is_valid_as_of (lib.rs:3502-3514), still native and branch-cheap. Stage 3 RANK BY rrf in Rust: build per-signal rank lists (vector = stage-1 similarity order; hops = BFS distance; recency = recorded_at from the node_versions projection; prop.X = caller-named numeric prop fetched in ONE batched SQLite query for the surviving candidate set only), fuse with caller weights and caller k — engine executes fusion near data, imposes zero policy (guardrail 2; RRF already validated as the pattern in NotiKeeper + GoVibe's 4-layer CONCEPT--HYBRID-RETRIEVAL-FTS-LAYER). Stage 4 materialize full rows for final LIMIT k only. Round-trips: 1 vs 3+ for Qdrant→Neo4j→app-RRF (each a localhost hop + JSON/gRPC serialization + client-side string-id join). Latency arithmetic from measured numbers: our legs ≈ 1.0-1.5 ms vector (P20/P33) + 2.5 ms hop-2/3-class BFS (P31) + µs fusion ≈ ~4 ms end-to-end; composition floor ≈ Qdrant server p50 3.3 ms (P20) + Neo4j hop 2.7+ ms (P23) + transport + join ≈ 7-10 ms. Verdict: round-trips win is STRUCTURAL (guaranteed); ≥2× end-to-end latency win is PLAUSIBLE-BUT-UNMEASURED — no G3-shape benchmark has ever been run (grounding report 4 is explicit), so per guardrail 3 this stays a hypothesis until the composition rig exists. The overlooked decisive axis: the composition CANNOT EXPRESS the query — Qdrant+Neo4j have no shared bitemporal AS OF; replicating `AS OF VALID x SYSTEM y` app-side requires schema gymnastics in two stores plus consistency between them. If latency only ties, expressiveness + single-store ops is the honest fallback moat claim.

## interval_semantics

Three temporal forms, two execution paths. (1) `AS OF "t"` — unchanged v1 valid-time point (valid_from <= t < valid_to, lib.rs:3502-3514), native string-compare in hot loops. (2) `AS OF VALID t1 [SYSTEM t2]` — two-axis point projection per the GoVibe ERD (valid_from/valid_to = business time; recorded_at/superseded_at = when GoVibe learned/replaced the fact): valid-time test as today PLUS recorded_at <= t2 AND (superseded_at IS NULL OR superseded_at > t2). Edges carry all four fields already (EdgeOutput, lib.rs:156-169; note superseded_by is never set on write paths today — must be wired in retract/supersede). Nodes do NOT: supersede_node overwrites the RAM slot (lib.rs:2777-2812), so node tx-time is served from the SQLite projection — a `node_versions(node_u32, version_seq, valid_from, valid_to, recorded_at, superseded_at, props_json)` append-only table populated by WAL replay (the projection retains what RAM discards; WAL remains authority per SPEC--SQLITE-SUBSTRATE §3.1). SYSTEM-axis queries and `VERSIONS OF x` are SQL-only paths; VALID-axis point checks stay native. (3) `DURING [a, b)` — interval overlap (valid_from < b AND (valid_to IS NULL OR valid_to > a)), compiled to SQL range conditions on composite indexes (valid_from, valid_to) in `edge_index` / `node_versions` tables; deliberately NOT added to the native BFS hot loop (overlap on frontier = one batched semi-join per hop, same pattern as property predicates). Hop-interval syntax: `DEPTH min..max` (emit nodes at depth >= min, stop at max; `*1..1` row-identical to single hop per SPEC--HQL-V2 §3.1), `TIER H0..H6` sugar mapping H-scale to hops with H6 = unbounded ceiling (adds the missing H6 to the grammar, STD--Execution-Governance §3; today tier stops at H5, hql.pest:87), `WIDTH n` = per-hop fan-out cap executing as deterministic truncation of each node's deduped candidate eid set — the W-scale separation "H governs hop depth; W governs fan-out" (STD §4) that no current knob provides.

## planner_line

Direct dispatch survives exactly as long as every query is ONE linear pipeline with a fixed stage order (seed → traverse → temporal → rank → clauses), each stage mapping 1:1 to one engine call, and the only runtime decision being a single constant cardinality threshold (prefilter-bitmap size → brute-force-exact vs filtered-HNSW). It fails the moment any of these appear: two seed stages joined (MATCH ... MATCH ...), branching/OPTIONAL patterns, statistics-driven reordering (should the filter run before or after the traverse?), or cost-based operator selection. This design stays inside the line by construction: (a) the grammar forbids composition beyond one pipeline — `|>` chains are fixed-order, one occurrence per stage kind (hql.pest rule shape, not runtime enforcement); (b) all genuinely hard planning — predicate index selection, join order inside WHERE — is delegated to SQLite's own query planner, which the mission explicitly permits ("no planner beyond SQLite's own"); (c) the Rust side's execute_hql grows from a 5-arm match to a ~8-arm match over (seed, Option<traverse>, Option<temporal>, Option<rank>) — still a flat, testable dispatch, no plan tree, no EXPLAIN, honoring SPEC--HQL-V2 §7's no-planner non-goal. The one acknowledged gray zone: the cardinality threshold is a two-strategy dispatch, i.e. a one-bit planner — we keep it a documented constant with a published crossover benchmark rather than an adaptive model.

## costs

Prereq B0 — SQLite substrate S0 (rusqlite embed, schema v1, replay watermark, 4 crash windows, snapshot coherence): C-3/HIGH per SPEC §2, ~2-3 weeks; already the committed direction, not new cost attributable to HQL. B1 — grammar v-next + AST + dispatch arms (pipeline, boolean WHERE with OR/NOT/parens, AS OF VALID/SYSTEM, DURING, DEPTH range, WIDTH, TIER H6, RANK BY rrf, VERSIONS OF) + fuzz-corpus extension (closing the P0-T8 gap): ~1.5-2 weeks, pure native, independently shippable per the track boundary rule (PLAN--HQL-REFINEMENT 2026-07-05 note). B2 — projection schema extension S2': node_props EAV + node_versions + edge_index temporal columns + label-anchor wiring + batched semi-join helper: ~2 weeks, C-3. B3 — filtered ANN: bitmap allowlist plumb-through + FilterT closure + brute-force-allowlist path + crossover bench: ~1-1.5 weeks (de-risked: search_filter verified in pinned hnsw_rs 0.3.4). B4 — native traversal upgrades: DEPTH range/WIDTH/lazy bindings/limit pushdown: ~1 week. B5 — RRF fusion operator + recency/prop signal fetch: ~1 week. B6 — benchmark harnesses: Qdrant filtered-search rig, LadybugDB/Neo4j var-length head-to-head (first apples-to-apples HQL-vs-Cypher per REPORT--HQL-V1-VS-V2 §4.4), and the first-ever G3 composition rig (Qdrant+Neo4j+app-RRF): ~2 weeks including the mandated ≥2-run/p50+p95/same-hardware discipline. Total: ~9-12 weeks single-maintainer, of which ~5-6 weeks is HQL-attributable (B1,B3-B5 + half of B6). Hard sequencing: capture the pre-P0 v1 baseline BEFORE merging the working-tree P0 changes (live process risk flagged in REPORT §4.2 — still possible, changes uncommitted).

## risks

(1) FFI-boundary death by a thousand rows: rusqlite is in-process (µs-class per prepared step) but per-row crossings during BFS would turn 22.6 µs hop1 into ms-class — mitigation is architectural (predicates evaluated once per candidate SET via batched IN-list/temp-table semi-joins, never inside the expansion loop) and gated by the S1 traversal gate (SPEC §5.3). (2) Ingest write amplification: durable insert is already the standing loss (48-60× vs COPY, P26/P30); SQLite apply adds a second write path — must be batched-transactional and async off the WAL apply, gated on P33 baseline (≥~1.9k vec/s at 1M). (3) Crash-window complexity across two stores (4 named windows, SPEC §4.4) — HIGH risk, C-3, the reason S0 exists as its own phase. (4) EAV node_props may be slow for range predicates on hot keys at 1M+ rows; fallback = promoted typed columns for declared-hot props (schema v2). (5) Two-axis correctness: superseded_by is never set on any write path today (lib.rs:2765, grounding report 2 §4) — SYSTEM-axis semantics are only as good as the wiring we add; needs its own test surface. (6) Recall under mid-selectivity filters is the known weak zone of filtered-HNSW everywhere; must be published, not hidden. (7) Bench fairness: every existing number is Level 0 maintainer-run (INDEPENDENT-BENCHMARKS.md); G1/G3 claims vs Qdrant carry the embedded-vs-server framing dispute — publish both framings. (8) Scope leak: VERSIONS OF + DURING + RANK BY is a lot of new surface for one program; B1 grammar must land behind tests before any B2/B3 execution work starts (DDD discipline per AGENT.md).

## honest_assessment

G1: latency bar reachable only under the deployment-honest framing (in-process engine vs Qdrant server — which is the real MSP/GKS consumer topology); against a hypothetical embedded Qdrant it is UNMEASURED and possibly a tie. Expressiveness bar NOT fully reachable: geo, nested-object filters, named/sparse vectors, multitenancy filters are renegotiated out — the honest claim is "Qdrant's boolean/range/match core + filter-aware ANN", not full DSL parity. G2: the ≤10%-slower bar is comfortably reachable (we start 7-190× faster on the GKS shapes) but is the WRONG bar to brag about — the honest statement is "expressively equivalent to a declared Cypher subset (linear + var-length + boolean WHERE + count(*)) and much faster on point/k-hop; still ~60× slower on bulk ingest and ~7× heavier on RSS pre-S1, and we do not offer OPTIONAL MATCH/shortest-path/general aggregation". G3: the round-trip win is structural and guaranteed; the "decisive end-to-end latency" win is a hypothesis with plausible ~2× arithmetic behind it but ZERO existing measurements (no G3-shape benchmark has ever been run). If the pilot bench shows only a tie on latency, the honest fallback per the mission's own contract is to renegotiate the moat claim from "faster" to "expressible at all": two-axis bitemporal AS OF + fusion in one statement has no app-composition equivalent without building a bespoke temporal layer across two stores — that claim survives a latency tie, but we must then say "the moat is expressiveness + ops surface, not speed" out loud. Node-level SYSTEM-axis time-travel is honestly a NEW capability enabled by the projection, not a recovered one — the in-memory engine never had it.

## switch_trigger

Abandon (or downgrade) Path B if any of: (1) S0/S1 gates fail — crash-window convergence cannot be proven within the stage budget, or the S1 RSS gate shows no meaningful reduction, or the traversal gate shows material hop-path regression (SPEC--SQLITE-SUBSTRATE §5.3) — then HQL v-next re-plans on Path A (native roaring-bitmap label/prop indexes, no SQL). (2) The B3 crossover bench shows the SQL-prefilter bitmap round-trip adds >30% p50 vs a native roaring prop-index prototype at 100k-1M scale across the selectivity sweep — SQLite loses its execution role and keeps only the props/versions storage role. (3) The G3 pilot shows app-composition (Qdrant+Neo4j+app-RRF, same hardware, warm, p50+p99) within 1.5× of our end-to-end — the latency moat is declared a mirage per the mission contract and G3 is renegotiated to the expressiveness claim only, with the RANK BY surface kept but no longer sold as a performance win. (4) SQLite apply drags durable ingest below ~1k vec/s or the graph-bench edge-ingest baseline by >25% (P31: 7.8 s / 800k edges) with batching already applied — the projection becomes rebuild-only (lazy, off the write path) and S2 predicate pushdown is cancelled. Each trigger has a measurable threshold and an already-named fallback; per guardrail 6, hitting one is a renegotiation with evidence, not a failure.
