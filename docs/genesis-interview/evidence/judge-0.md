# VERDICT
Design A wins on the performance lens: it is the only design with a mechanically credible G1 path (native roaring payload bitmaps + verified hnsw_rs 0.3.4 search_filter + O(1) two-regime switch — literally Qdrant's pre-filter strategy minus SIMD), it keeps the crown-jewel native traversal untouched, and its characterization of the crate's filter semantics is the accurate one (I read the pinned source: filter applies at result-collection during descent, navigation unfiltered — A right, B overstated). B's G1 routes a µs-class latency budget through per-query SQLite EAV ID-set materialization (ms-to-tens-of-ms at mid selectivity) and is schedule-blocked behind the C-3/HIGH S0 substrate; its own switch trigger will likely fire. C is the cheapest and most honest but concedes G1 below ~10% selectivity by construction — its 'brute-force floor' is actually O(N) over the whole collection (the existing escape hatch, lib.rs:3576, has no candidate-restricted mode without a payload index), which is a cliff, not a floor. On G2 all three inherit the measured 7-190x dominance on GKS-shaped bounded traversals (the <=10% bar is already exceeded; the real risk is columnar-CSR-style large-frontier scans, which all three correctly scope out). On G3 all three converge on the same fused pipeline and the same honest ~2-3x-vs-server-composition arithmetic; note A's '>=3-5x' sums composition legs that a competent app would run in parallel — the composition floor is max(legs)+join ~4-5ms, not the sum, so the realistic margin vs a tuned colocated composition is ~1.5-2.5x, which is exactly why C's moat-bench-as-co-equal-deliverable must be grafted onto A. No design beats an embedded, SIMD-tuned Qdrant on raw kernel throughput (hnsw_rs ships scalar/SSE2-autovec only; Qdrant has AVX2/AVX-512 kernels, ~4-8x per distance eval) — the G1 latency win is a deployment-category win against Qdrant-as-deployed and every design that says so plainly (A, C) is being honest; the bench must publish both framings. Winner: A, at ~1.5-2x its stated 41-46 dev-days, with C's benchmark discipline and B's node_versions projection grafted on.

# REFUTATIONS
- [B] CLAIM: filtered candidates are rejected DURING graph descent, not post-truncated; recall loss of post-filter disappears
  REFUTED: Read the pinned crate (hnsw_rs-0.3.4/src/hnsw.rs:983-1041): the filter is applied only when pushing into the return_points result heap; candidate expansion and navigation are unfiltered, and the termination/pruning conditions compare against the sparsely-filled FILTERED heap. At low selectivity return_points may never reach ef (latency blows up as the loop keeps expanding) or terminates with fewer than ef genuine matches (recall loss). There is no internal ef inflation in the crate and Design B proposes none (Design A does, explicitly). 'Reduced recall loss' is defensible; 'disappears' is false.
- [A] CLAIM: ~4096 scalar-L2 evals at dim 1024 ~ low-single-digit ms worst case (Regime A brute-force)
  REFUTED: The compute math is right (~4M FLOPs ~ 1-4ms) but omits I/O: post-P0 the f32 rerank sidecar is OFF-RAM (SidecarReader, positioned reads, LRU of SIDECAR_CACHE_ROWS=4096 rows, lib.rs:1038). A cold Regime-A pass at the default threshold T=4096 is ~4096 random 4KB positioned reads on a SATA SSD (~50-100us each) ~ 200-400ms worst case — two orders of magnitude off — and since T exactly equals the LRU capacity, one cold query evicts the entire cache, poisoning the next query. The threshold must be sized against warm-cache residency or the arena (RAM) copy, not the sidecar; A's design text never distinguishes warm from cold here.
- [A] CLAIM: latency plausibly >=3-5x [vs the Qdrant+Neo4j+app-RRF composition]
  REFUTED: The arithmetic sums the composition's legs (3.3ms Qdrant + 2.7+ms Neo4j + join). A competent composition issues the vector and graph legs concurrently (or pipelines seed->hop with streaming), so its floor is max(legs)+join ~ 4-5ms, not 6-10ms. Against A's own 2-4ms fused estimate that is ~1.5-2.5x, not 3-5x — which lands exactly inside A's own switch-trigger (2) territory (<1.5x = mirage). Also the 3.3ms Qdrant p50 was measured through Docker-on-Windows (WSL2 NAT) networking, which inflates the composition's apparent cost vs a Linux deployment. The round-trip and single-timestamp-AS-OF-consistency wins are structural and safe; the 3-5x latency multiplier is not.
- [B] CLAIM: SQLite contributes ... batched frontier semi-joins for property predicates — one prepared statement per hop, never per row [while hop1 22.6us stays the crown jewel]
  REFUTED: A prepared statement with a temp-table/IN-list join over a 10k-node frontier costs ~1-10ms per hop in SQLite (row materialization + index probes through the rusqlite boundary), i.e. 50-500x the 22.6us hop1 budget. Any traversal carrying a property predicate becomes ms-class per hop — the crown-jewel numbers survive only for predicate-free traversals, which is exactly the case where SQLite contributes nothing. The design sells both facts without connecting them.
- [B] CLAIM: Prereq B0 [S0 substrate] ... already the committed direction, not new cost attributable to HQL
  REFUTED: Accounting spin. B's G1 (bitmap from SQL), SYSTEM-axis temporal, VERSIONS OF, and label anchors are all hard-blocked behind S0 (C-3, HIGH risk, 4 named crash windows, 2-3 weeks) and the S2' schema extension. Whether or not the cost is 'attributable', the mission targets cannot ship until it lands — B's wall-clock delivery risk includes the substrate's failure modes, and its own switch trigger (1) admits the whole path re-plans onto Path A if S0/S1 gates fail. A design whose fallback is its competitor is conceding the risk profile.
- [C] CLAIM: bottoming out in the exact-brute-force escape hatch that already exists (lib.rs:3576-3596)
  REFUTED: That hatch triggers when fetch >= collection size and enumerates ALL slots — it is O(N) over the whole collection, not O(|filtered set|). Without any payload index/bitmap, C has no candidate-restricted brute force: at 100k x dim-1024 the 'floor' is a full-collection exact pass through the off-RAM sidecar (~400MB of positioned reads, hundreds of ms). A and B's bitmap-driven Regime A is O(|bitmap|); C's is a cliff dressed as a floor, and it makes the low-selectivity G1 loss worse than C's own honest assessment states.
- [C] CLAIM: compile the WHERE expr to a Fn(&NodeOutput) -> bool closure ... zero engine risk / deliberate duplication with S2 documented in the ADR
  REFUTED: Understates the collision: committed S1 (SPEC--SQLITE-SUBSTRATE) moves node props OFF the resident node map — 'traversal must not need resident props' is a stated S1 gate. C's predicate closure reads exactly those resident props on the G1 hot path; post-S1 every predicate eval becomes a SQLite read anyway, silently converting C's native pushdown into B's SQL round-trip without the batching design. The duplication is not 'deliberate and stable', it has a built-in expiry the design never prices in.
- [A] CLAIM: SEARCH ... FILTER ... EXPAND ... RANK BY stays inside the planner line because the only runtime choice is one bitmap.len() <= T comparison
  REFUTED: Slightly self-serving: the design also ships ef_eff = min(ef/max(s,0.05), 4*ef) — a selectivity-driven parameter model — plus a WARN-tagged scan fallback for unindexed predicate leaves. Each is individually O(1), but together they are the embryo of a cost model (selectivity estimate -> parameter choice -> strategy choice). Still the safest G1-capable design, but the claim of ZERO cost-model content is not quite true; the T and ef_eff constants must be frozen and bench-published or they will grow adaptive.
- [B] CLAIM: against a hypothetical embedded Qdrant the outcome is unmeasured and possibly a tie
  REFUTED: On raw kernel throughput it is likely a loss, not a tie: Qdrant ships hand-tuned AVX2/AVX-512 SIMD distance kernels plus segment-parallel search; the engine's hnsw_rs 0.3.4 is built with no SIMD feature (Cargo.toml:66 — no simdeez) and exact_l2 is a plain scalar loop, ~4-8x slower per distance eval at dim 1024. All three designs inherit this, but only A and C explicitly frame the G1 latency claim as a deployment-category (embedded-vs-server) win; B's 'possibly a tie' is the softest and least honest framing of the same fact.
