All three converge on the same G2/G3 core (native BFS + WIDTH/FANOUT + var-length + lazy rows + Rust RRF over u32 ranks, moat-bench as first-ever G3 evidence), which raises confidence that core is right.

# REFUTATIONS
- [B] CLAIM: all genuinely hard planning — predicate index selection, join order inside WHERE — is delegated to SQLite's own query planner, which the mission explicitly permits ("no planner beyond SQLite's own")
  REFUTED: Fabricated permission. The quoted phrase appears nowhere in the mission guardrails; guardrail 1 says 'No planner tar-pit — pipeline DSL with fixed operator shapes only.' Delegating predicate planning to SQLite does not make planner risk vanish — it relocates it: EAV join-order or index-selection changes in SQLite's optimizer (or an ANALYZE run) silently change HQL query latency class, which is exactly the cost-based-optimizer failure mode the project deleted LogicalPlanner to avoid, now outside the maintainer's code and diff review.
- [B] CLAIM: filtered candidates are rejected DURING graph descent, not post-truncated; recall loss of post-filter disappears
  REFUTED: Verified against the pinned hnsw_rs-0.3.4 source: in search_layer (hnsw.rs:913-1048) the filter gates only insertion into return_points (lines 1028-1041); the candidate/navigation heap traverses filtered-out points freely and ef-budget is still spent visiting them. This is result-collection filtering with extended termination, not descent-time pruning, and it does not guarantee k passing results. Mid-selectivity behavior is closer to post-filter-with-larger-search than to Qdrant's filter-aware HNSW. Design A describes the same primitive accurately; B oversells it while resting its 'recall loss disappears' claim on the overstatement.
- [B] CLAIM: the already-committed engine-owned SQLite projection ... Prereq B0 ... already the committed direction, not new cost attributable to HQL
  REFUTED: Dependency laundering. Only the ADR is committed; docs/SPEC--SQLITE-SUBSTRATE-S0-S1.md is an untracked working-tree file (git status '??') and zero substrate code exists. B's G1 (B3 filtered ANN) requires B2 (node_props EAV) which requires B0 (S0: rusqlite embed, 4 proven crash windows, C-3/HIGH risk per the spec itself). Booking '~5-6 weeks HQL-attributable' while the entire G1 deliverable is hostage to the riskiest unshipped infrastructure in the program is self-serving accounting; if S0 slips or fails its gates, Path B delivers no G1 at all (its own switch trigger 1 concedes this by falling back to Path A).
- [B] CLAIM: seed_stage = search | hybrid | match_pattern | traverse | context // any existing command
  REFUTED: Crosses B's own planner line. match_pattern rows are multi-variable binding maps (full node/edge JSON per binding, lib.rs:3157-3163) — piping them into a TRAVERSE stage requires choosing WHICH bound variable is the frontier, a binding-selection/join decision, i.e. the 'two seed stages joined' shape B's planner-line section names as the breaking point. CONTEXT returns a ContextPackage (nodes+edges+super_nodes+reasoning_path, lib.rs:208-214), not a rankable row set — as a RANK BY seed it has no defined rank list. A and C restrict seeds to search|hybrid for exactly this reason; B's generality is unexamined surface that invites the tar-pit through the grammar.
- [A] CLAIM: ~4096 scalar-L2 evals at dim 1024 ≈ low-single-digit ms worst case
  REFUTED: Ignores IO. For quantized collections (SQ8/BQ — the configurations that motivate the sidecar), exact scoring in Regime A reads f32 rows from the OFF-RAM sidecar via positioned reads (SidecarReader, lib.rs:1052-1058; post-P0 design is explicitly non-resident). A cold brute-force over 4096 rows = ~4096 random 4 KB reads (~16 MB) on the bench machine's SATA SSD — tens to hundreds of ms, not single-digit. Worse, the working set sits exactly at SIDECAR_CACHE_ROWS = 4096 (lib.rs:1034-1038), so successive queries with different filter bitmaps thrash the LRU. The compute-only estimate holds only for f32 arenas (in-RAM) or warm caches; the threshold T's default and the Regime-A latency budget must be re-derived with cold-IO in the model.
- [A] CLAIM: E2: MATCH (a {id:"g0"})-[:LINK*1..6]->(b) FANOUT 100000 ... // FANOUT here = frontier row cap, hard error on breach
  REFUTED: One keyword, two semantics: in TRAVERSE/EXPAND, FANOUT is a per-node per-hop W-scale breadth cap that silently truncates (take first n by sorted edge key); in pattern MATCH it is a global frontier row cap that hard-errors. A caller who learns FANOUT from E3 (FANOUT 5 = W2 governance) will misread E2's FANOUT 100000 completely — and 100000 contradicts the W-scale framing (W4 danger = 9+) used to justify the keyword. SPEC--HQL-V2 §3.2 already names the frontier concept separately; the design should keep two keywords (FANOUT vs frontier cap) or it ships a spec-level footgun.
- [A] CLAIM: pipeline = { (search | hybrid) ~ pre_filter? ~ expand? ~ temporal? ~ rank_by? ~ clauses } ... all additions keep every v1/v2-P0 query parsing identically
  REFUTED: The sketch doesn't demonstrate the compatibility claim: the embedded `search` rule already terminates in its own `clauses` (and `as_of`), so the pipeline production carries clauses twice and two as_of sites (search's internal as_of vs pipeline temporal) — `SEARCH x K 5 AS OF "t" WHERE ...` now has ambiguous ownership of AS OF and WHERE, and PEG greediness will bind them to the inner rule, making pipeline-level temporal unreachable after a seed that consumed as_of. Resolvable (factor a seed-core rule without trailing clauses), but as written the grammar is inconsistent and the 'parses identically' claim is asserted, not shown.
- [C] CLAIM: This path deliberately does NOT build ... filter-aware HNSW graph pruning (ACORN) ... real filter-aware HNSW (ACORN-class, inside hnsw_rs or a fork) is required — that exceeds minimal-delta scope
  REFUTED: False dichotomy that costs C its G1. The pinned hnsw_rs 0.3.4 already ships FilterT + search_filter (verified: filter.rs:7-24 incl. closure blanket-impl, hnsw.rs:1475) wired at the single seam C itself identifies (VecIndex::search_f32) — using it is days of wiring plus a bitmap, not a fork or research. It is not ACORN-grade (result-collection filtering, see the B refutation), but it strictly dominates C's post-filter-at-metadata-join: the search keeps expanding until ef PASSING points are collected instead of truncating then re-searching. C's own risk 8 admits the refetch loop doubles HNSW work in the worst case — paying that to avoid an API that already exists is the design's one clearly wrong call.
- [C] CLAIM: tier = { "H0".."H6" } // adds H6
  REFUTED: Minor but symptomatic sketch error: pest's `..` range operator works on single-character terminals, not multi-character string literals — `"H0".."H6"` is not a valid pest production (the working grammar enumerates alternatives, hql.pest:87, for this reason). Trivially fixed, but in a design whose whole thesis is 'the delta is small and precise', the grammar delta being its least-checked artifact undercuts the minimal-delta credibility.
