# รายงาน — MARK XV P1: RSS + Disk × Quant × Scale (ถึง 1M nodes)

**วันที่:** 2026-06-24 · **เอนจินที่วัด:** main `1c030b9` + ส่วนขยาย harness ·
**เครื่องทดสอบ:** RAM 32 GB, ดิสก์ C: เหลือ ~34 GB ตอนเริ่ม · **ข้อมูลดิบ:** [AUDIT--P33](AUDIT--P33-RSS-QUANT-MATRIX.md)

---

## 1. บทสรุปผู้บริหาร

วัดการใช้ **หน่วยความจำ (RSS)** และ **พื้นที่ดิสก์** ของเอนจินในทุกการตั้งค่า
quantization `{none, sq8, bq} × {rerank เปิด/ปิด}` ตั้งแต่ 100k จนถึง **1,000,000 nodes**
(มิติเวกเตอร์ 1024) เพื่อพิสูจน์คำกล่าวอ้างเรื่องการประหยัด RAM/disk ของ quant
และหาเพดานสเกลจริง

ข้อสรุปสำคัญ 3 ข้อ:

1. **RAM:** ที่ 1M nodes f32 ใช้ **11.4 GB (ใส่ลงเครื่อง 32 GB ได้)**; SQ8 เล็กกว่า **2.06×**,
   BQ เล็กกว่า **2.93×** — *น้อยกว่า* อัตรา 4×/32× ต่อเวกเตอร์ เพราะมี "พื้นกราฟ+เมตาดาตา"
   ~3.6 GB ที่ quant ลดไม่ได้ครอบงำอยู่ → **กราฟคือพรมแดน RAM ถัดไป ไม่ใช่เวกเตอร์**
2. **Disk:** ไฟล์ arena `vec_*.bin` เล็กลง **4.0× (SQ8) / 32× (BQ) ตรงเป๊ะ** ตามที่ ADR อ้าง
   แต่ rerank เพิ่มไฟล์ f32 sidecar กลับเข้ามาเต็ม → snapshot ของ quant+rerank **ใหญ่กว่า** f32 ล้วน
3. **⚠ ข้อค้นพบเด่นด้านปฏิบัติการ:** ไฟล์ WAL (`genesis-graph.wal`) **ไม่เคยถูกบีบอัด** เก็บเวกเตอร์ดิบ
   → โตถึง **~20.4 GB ที่ 1M** ใหญ่กว่า snapshot 5–51 เท่า ทำให้ดิสก์เหลือแค่ **2.1 GB** และ
   ทำให้บันทึก snapshot ล้มเหลว **นี่คือเพดานดิสก์จริง ไม่ใช่เวกเตอร์**

---

## 2. วิธีการ (Method)

- **คลังข้อมูล:** synthetic-clustered มิติ 1024 (เครื่องกำเนิดเดียวกับ P32, seed 42)
  - 100k–500k: ใช้ส่วนนำหน้า (prefix) ของชุด 500k ผ่านพารามิเตอร์ `GB_LIMIT`
  - 1M: สร้างชุด `gb_vbench_1m/` ใหม่ (4.096 GB, สตรีมตอนสร้าง, ไม่ทำ ground truth เพราะไม่วัด recall)
- **เอนจิน/harness:** `benches/vbench_genesis.rs` (ขยายเพิ่มสำหรับงานนี้) แก้จุดบกพร่อง 4 ข้อก่อนวัด (ดูหัวข้อ 5)
- **ค่าคงที่:** `efc = 200`, `ef_search` = ค่าเริ่มต้น, `k = 10`, `q = 200`
  วัด RSS ด้วย `sysinfo` หลัง ingest + flush; วัดดิสก์จากขนาดโฟลเดอร์ `gdb` (แยก WAL ออก)
- **ข้อจำกัดขอบเขต:** ผลในรายงานนี้ใช้ได้กับ **RAM/latency/disk เท่านั้น** ไม่ได้วัด recall

## 4. ข้อค้นพบ (Findings)

- **การคาดการณ์จาก 500k แม่นยำมากที่ 1M** — คาด f32/sq8/bq = 11.2/5.6/3.9 GB,
  วัดจริง **11.4/5.5/3.9 GB**; อัตรา quant คงที่ข้ามสเกล (500k: 2.04×/2.90× → 1M: 2.06×/2.93×)
- **f32 ที่ 1M ใส่เครื่อง 32 GB ได้** (RSS 11.4 GB) เมื่อสตรีม corpus แทนการโหลดทั้งก้อน
- **เทียบ P31:** f32 เคยใช้ 12.6 GB @1M ก่อนทำ interning → ตอนนี้ 11.4 GB = **ลดลง ~9.5%**
  (น้อย เพราะที่ 1024 มิติ เวกเตอร์+กราฟครองพื้นที่มากกว่าส่วน node-id ที่ interning ลดได้)
  → **quant เป็นคันโยกลด RAM ที่แรงกว่า interning มากที่มิติสูง**
- **อัตรา 4×/32× บนดิสก์เป็นจริง — เฉพาะไฟล์ arena** (`vec_*.bin`); แต่ snapshot รวมลดได้น้อยกว่า
  (3.3× / 10.3×) เพราะเมตาดาตาไม่หด
- **rerank กินทั้ง RAM และดิสก์ ไม่ได้ช่วยประหยัด** — เก็บ f32 sidecar เต็ม ทำให้ snapshot
  ของ quant+rerank ใหญ่กว่า f32 ล้วน; เป็น "ประกัน recall" ที่ต้องจ่ายด้วยพื้นที่
- **⚠ WAL คือเพดานดิสก์จริงและโตไม่จำกัด** — ~2.1 GB @100k, **~20.4 GB @1M** (5–51× ของ snapshot);
  ที่ 1M ทำให้ดิสก์เหลือ 2.1 GB และบันทึก snapshot ไม่สำเร็จ **เป็นปัญหาด้าน durability/ops ไม่ใช่เรื่อง quant**

## 5. จุดบกพร่องของ harness ที่แก้ไป (เพื่อให้ตัวเลขเชื่อถือได้)

`benches/vbench_genesis.rs` ก่อนงานนี้:

1. **โหลด `corpus.f32` ทั้งก้อนเข้า RAM ก่อน ingest** (~8 GB ที่ 1M) → ทั้ง **OOM ที่ 1M** และ
   **ทำให้ตัวเลข RSS เกินจริง** ~2 GB ที่ 500k → แก้เป็น **สตรีมจากดิสก์ทีละ 10k แถว**
2. **ไม่เคยเรียก `flush_index()`** → backlog ของ HNSW (async) อาจยังไม่ลงดัชนีตอนวัด ทำให้ **นับกราฟขาด** → แก้ให้ flush ก่อนวัด
3. **ขับเฉพาะเส้นทาง f32 single-space เดิม** → วัด quant/rerank ไม่ได้ → เพิ่ม `create_collection(quant, rerank)` + env `GB_QUANT`/`GB_RERANK`/`GB_LIMIT`
4. **วัดดิสก์รวม WAL** ที่บดบังขนาด snapshot → แยกนับ snapshot (`.bin` + `state.json`) กับ WAL คนละส่วน

## 6. สถานะ & งานที่เหลือ (MARK XV P1)

| รายการ | สถานะ |
|---|---|
| RSS + disk ถึง 1M | ✅ เสร็จ (รายงานนี้ + AUDIT--P33) |
| สเกล 2M | ⛔ ติด — WAL จะโตถึง ~40 GB เกินดิสก์ว่าง ต้องบีบอัด WAL ก่อน |
| Recall บน embedding จริง | ⏳ ยังไม่วัด — ชัยชนะของ BQ ด้าน RAM/latency/disk ยัง "ไม่มีความหมาย" จนกว่าจะพิสูจน์ความแม่น (BQ ไม่มี rerank ทำให้เวกเตอร์ทิศเดียวกันต่างขนาดยุบรวมกัน) |

**สิ่งที่ผมทำต่อให้แล้ว:**
- เพิ่ม **WAL compaction/rotation** เป็นรายการอันดับแรกของ MARK XV P3 ใน [ROADMAP.md](../ROADMAP.md)
- สร้าง task chip แยกสำหรับลงมือแก้ WAL (truncate หลัง snapshot)
- เก็บกวาดโฟลเดอร์ `gdb` ชั่วคราว → ดิสก์ว่างกลับมา **31.6 GB** (corpus 1M 3.8 GB ยังเก็บไว้สำหรับงาน recall)

**ขั้นถัดไปที่แนะนำ:** ตั้ง harness วัด recall บน embedding จริง (อีกครึ่งของ P1) และเริ่มงานบีบอัด WAL
